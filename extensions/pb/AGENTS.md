## Project map: extensions/pb/

### Session-keyed state (extensions/pb/kit.ts, extensions/pb/hooks.ts)
- Every in-memory registry keyed by a session path lives in `kit.ts` and must be cleared in `pruneSession`, which hooks.ts's `session_shutdown` handler calls after `cleanupIndexes`. A session-keyed map added elsewhere leaks for the life of the pi process (keys are session file paths); pinned by "session shutdown prunes every session-keyed registry for that session".
- Prune covers memory only, on purpose: the disk-side per-session files are not swept — `reviews/<sha1>.json` must outlive its session because it is the fail-closed read-only guard above, and orphaned `baselines/*` are a separate decision.
### Spec write gates (extensions/pb/spec.ts, extensions/pb/kit.ts, extensions/pb/spec-tools.ts)
- The write tools refuse only what the parser can decide: parse errors, required sections, unique task ids and cited `path:line` claims. Semantic shape — Threats, measurements, evidence, reasons, Contracts, migration answers, proof quality — is the reviewer's and the human's job.
- Task acceptance is the only review checklist: `acceptanceCriteria` (`spec.ts`) yields `T1.1`, `T1.2`, … from each task's `- Acceptance:` lines. A task's `Test:` command is its proof; there is no per-line proof-marker or mapping layer.
- A `replace` whose body is blank is refused in `pb_update_spec`: the heading would stand over nothing and silently empty what later readers and the reviewer rely on.
- The writer-facing format is `SPEC_FORMAT` (`extensions/pb/prompts.ts`); its guidance is advice the reviewer checks, not a rule a write gate enforces.
- Evidence has one rule, `EVIDENCE_RULE` (prompts.ts, built on `LOAD_BEARING`), embedded word for word in the writer's format, `SPEC_REVIEWER_SYSTEM`, `SPEC_CLAIM_CHECK_SYSTEM` and `SPEC_FIX_RULES`; never restate it in a section or role — change it there. Pinned by "evidence: the writer, the spec reviewer, the claim check and a repair lap judge claims by one rule".
- Only load-bearing claims need evidence: a value the change itself defines is proven by the Acceptance line that pins it, a claim about existing code or a service never is (a test written from the same belief passes anyway).
- Not overengineering is one rule, `OVERENGINEERING_RULE` (prompts.ts): build for the needs the change has, the cleanest design within them, never the smallest at the price of debt. `PLANNER_ROLE`, the `Overengineering` spec check, `CRAFT_RULE`, `fixSeedPrompt` (with `FIT_RULE`) and `REVIEWER_SYSTEM` carry it word for word; never reintroduce "smallest change" or "simplest thing" wording.
- The dependencies a change adds are read, not noticed: `addedDependencies` (manifest.ts) compares each changed manifest's `dependenciesIn` at the base (`git show`, bounded) and now (`readManifest`), for the project and each sibling repository, and the review brief lists them.
- What a spec must survive is one list, `SPEC_CHECKS` (prompts.ts): the writer runs it before writing (`SPEC_SELF_CHECK`, in `specPrompt` and `finishSpecPrompt`) and `SPEC_REVIEWER_SYSTEM` checks the same lines (pinned by "spec checks: the writer runs the spec reviewer's checks before writing, from one list"). A new check goes into the list, never into one side only.
- `specLosses` (`spec.ts`) names what a write removed from the previous text (sections, Acceptance lines, Decisions entries, compared word for word); both write tools add it as a note, never a refusal — a revision may drop things on purpose.
- An assumption is written one way, `assumed: <what would falsify it>` right after its claim; `specAssumptions` (`spec.ts`) is the only parser — it also reads the older Decisions lines starting "Assumption" and skips the build's own "Assumption (build, …)" entries. The approval summary and the review's scope count come from it.
### The spec review (extensions/pb/prompts.ts, extensions/pb/spec-review.ts)
- One independent pass on the frozen draft: `SPEC_REVIEWER_SYSTEM` carries every reviewer rule and `specReviewBrief` only the spec text plus "only a P0 blocks". There is no round, carry, delta or outside lane machinery to keep in sync.
- `runSpecReview` records `{ type: "spec-review", verdict: "pass" | "block" | "error", hash: specHash(md) }`: a run that reports no findings call is `error` and never reads as a pass. `ensureSpecReviewed` reuses a pass or block on the same hash, re-posts a standing P0, and otherwise reviews.
- P1–P3 are posted as advisory and do not hold the build; at the build door the build-start screen (`openP1s`, build-start.ts) asks, for a P1 on the text about to be approved: build anyway / repair first / stop — shown again when the pass was reused silently, skipped when that text is already approved, defaulting to build with a note when nobody can answer. A choice, never a gate.
- A finding carries the check it fails (`check`, one of `SPEC_CHECK_NAMES`, read off `SPEC_CHECKS`); `toFindings` maps an unknown tag to `Other`, so model text never mints a category. `/pb:stats` counts them per check (`SpecPhase.byCheck`).
- A spec edited while the review runs is not built: the pass is discarded and the human is asked to rerun `/pb:build`, which reviews the new text. The placement dialog after the pass is guarded too: `startBuild` re-reads the spec and compares `specHash` against the reviewed text right before any `approveSpec` (the sub-second gap before a fresh session's approval stays uncovered on purpose).
### Spec repair laps (extensions/pb/repair.ts, extensions/pb/prompts.ts)
- A lap repairs the **plan**, in a fresh session of its own (`driveRepair`, repair.ts: `spec-fix: <spec> · lap N`, parented to the session that started the run, on that session's model through the carry) — never in the planning conversation, whose planner role and stale beliefs are not the lap's. It is not a fresh run: it has `pb_try` (read-only probes), `pb_ask` (you) and the ordinary spec pen.
- A lap writes through the spec tools (`pb_update_spec` section by section, `pb_write_spec` when most of it changes), so the write gates and standards still bind it and `specLosses` names anything a write removed. `SPEC_FIX_RULES` is its contract: point a claim at evidence, delete it, decide it in `Decisions`, or tag it `assumed:`; a finding that is wrong gets a rebuttal citing `path:line`.
- A lap never invents a worklist: `recordedFindings` (spec-review.ts) numbers only the findings recorded for the exact text now on disk, and no finding is carried across an edit. Before reporting it runs `SPEC_CHECKS` over what it changed (`specFixPrompt`), so a lap that settles one claim does not write two new ones.
- `Progress.fix` (`store.ts`) is the whole authority on a lap: it names the one session allowed to report, says whose turn is owed (`stage: "lap"` → the model has the ball, `"advance"` → pb does), and survives a restart. `pb_spec_fix_done` refuses any other session, refuses numbers its brief didn't show, and refuses a report that leaves one of them out.
- One lap per session, always: `openRepair` (repair.ts) refuses a second while another lap is live in the calling session (a dead one is dropped instead), so a report always closes the lap its session owns. `advanceSpecFix` (repair.ts) is the **only** step-forward, and `driveRepair` runs it in the starting session after each lap, for both doors, so every result lands where the human planned.
- `agent_settled` only drops a lap whose plan a build took: an unreported lap stops and says so; an unchanged text is not re-checked or re-reviewed; parked questions are asked before anything else; a manual `/pb:spec-fix` lap stops at its claim check, and only the driver chains another lap.
- The driver runs the claim check **once per run** (`SpecFixState.claimCheck`, carried across laps), after the first lap and before any confirming review; its claims get a lap only while `laps < maxLaps - 1` when a review is still in budget, so claim laps never spend the lap the confirming review's findings need.
- Claims handed to a lap are not re-checked, so the digest says they were sent to a lap (`claimsTaken`), never that none are left.
- What a lap repairs by default is `repairable` (spec-review.ts): P0–P2, for both doors; P3 only when named. A review that reports nothing (or whose text changed under it) stops the run: no digest claims a verdict on text no review read. `fixLive` drops a lap whose session file is gone or older than six hours, so a killed session cannot lock a spec out of repair.
- The claim check (`spec-check` role, `SPEC_CLAIM_CHECK_SYSTEM`) is the cheap pass that makes unattended repair safe: it answers only which load-bearing claims carry no evidence and no `assumed` tag; new subjects are the spec reviewer's job. A check that reports nothing is `error` and stops the run rather than reading as clean.
- `/pb:spec-harden`'s stop rule is facts, not silence: budgets (`specFix.maxLaps`, `specFix.maxReviews`, defaults 3 and 2), nothing left to repair, or a lap that changed nothing. A fresh full review never runs out of subjects, so "no findings" is never the condition. `/pb:spec-fix` is the manual single lap; the hardening driver's `driver: true` is the only difference in the lap record.
### Build, checks and undo (extensions/pb/build-loop.ts, extensions/pb/build-start.ts, extensions/pb/undo.ts, extensions/pb/checkpoint.ts, extensions/pb/store.ts, extensions/pb/verify.ts)
- Prompts carry paths, never documents: `specReference` (`prompts.ts`) names the spec file and `BINDING_SECTIONS`, and every handout, retry, coherence pass, reset summary and fix seed uses it, so nothing pasted to a builder is shortened or stale and no text budget is needed.
- Two briefs carry documents on purpose: the spec-review pass gets the whole frozen draft (it judges the hashed text, and the hash reuse depends on the exact bytes), and the review diff reaches reviewer and verifier because they have no shell to produce it (`REVIEW_DIFF_CHARS`, the same frozen capture for both). `checkpointSummary` pastes the specs it resets to — the summary is the reset.
- A build resets between tasks by default (`buildReset: "task"`): `turn_end` resets at the task boundary to `stateSummary`, and `doneHandoff` names each finished task's checkpoint files in the next `taskPrompt`, directing it to inspect the parts it depends on. The reset happens only between tasks — never mid-task or between failed attempts.
- `"threshold"` keeps the `checkpointAt` trigger and `"never"` leaves compaction to Pi.
- The build is autonomous: `pb_ask` refuses inside a build (`phase === "building"`), `buildMechanics` says so, and there is no pre-T1 implementer validation. An ambiguity is a `pb_record_decision (assumption: true)`; only a Goal or a Contract that cannot be built as written stops it — `pb_task_done blocked` pauses with tip `build.contract`, and `/pb:build` re-approves the revised spec and resumes.
- That re-approval is not unconditional: when the live contract hash differs from the approved one, `contractDiff` shows every changed block and a confirm gates the `approveSpec` — the model gets turns while paused too, so "edited while paused" is proven to the human, not assumed.
- `startBuild` also clears the session's `pendingBuild` record: one that survives would keep `agent_settled`'s stop-pause from firing for its TTL.
- A red proof is one field, bound to the exact `Test:` command: `syncTasks` drops `TaskProgress.redCommand` when the command text changes; a repeat `pb_tests_red` replaces the proof (only the latest failed run counts) and a passing run clears it. A task whose tests never fail is refused by `pb_task_done` and told to stop with status `blocked`.
- A command an earlier finished task already proved cannot fail again: `earlierProof` (`spec.ts`) derives that exemption from the task list (nothing stored) and the disclosure reaches the reviewer through `redNotes`.
- Checkpoints live in refs/pb/checkpoints with a **per-process** private index (`pb-index-<pid>`): never use a shared index file, parallel sessions would fight over one lock, and a lost lock means a lost checkpoint. `restore` leaves files that drifted since its `from` snapshot alone and reports `guardFailed` instead of clobbering.
- `snapshot()` returns the ref tip when the written tree equals the tip's tree: no commit is minted and the ref does not move, so a fresh snapshot of an unchanged tree is not new information (the commit message is git-only; nothing human reads it).
- The ref moves only by compare-and-swap (`update-ref <ref> <new> <old>`, empty `<old>` = must not exist): two concurrent pb processes would otherwise let the later writer rewind the tip past the earlier commit and orphan the rows that name it; a lost race re-parents against the fresh tip, eight tries, then no snapshot rather than an orphan. Pinned by the concurrent-snapshot storm test.
- `appendCheckpoint` (`store.ts`) is the only way a `/pb:undo` row is added: it compares against the **last element of the list being written** — pass a filtered/sliced list, not the stored tail — and counts row identity (`id`/`task`), so another step's row is never dropped and freshly-numbered `uN` rows are exempt. `beginTask` and `beginCohereEntry` save only when it returns true.
- `specWarnings` warns, without rejecting, when two tasks share one `Test:` command: one run cannot show each task's own new tests failing.
- Where lint gates a build is decided once, at its start, and stored as `Progress.lintGate` (`lintGateFor`, build-start.ts): a configured `"lint"` means `"task"`; an auto-detected one only when the planning session's baseline ran it clean, else `"final"`, so debt already in the code never fails T1. A restart keeps the stored gate; a build without one stays per-task (`lintsEachStep`).
- With `lintGate` `"task"`, lint gates every step, not just the end: `checkAndAdvance` runs `lintCmd` after the step's own check and fails the step on it; the final step skips lint when entered straight from a passed step (`lintDone`) and re-runs it on a retry. A task records one `check` event per attempt with a `lint` field, which is where stats and the completion's lint fact come from.
- `doneHandoff` names, per file, what each finished task declared (`Checkpoint.declarations`, from `addedDeclarations` → `declarationsIn` in `extensions/pb/declarations.ts`: per-language patterns over added diff lines, test files skipped, capped), so a task after a reset extends a helper instead of writing a near-copy. A heuristic: a miss costs a pointer, never correctness.
- What pb runs when a task reports done is `taskDoneCommands` (kit.ts): its check, then its own `Test:` when it proves itself red, so the green half of the red proof is pb's, not the model's word; the handout names the same list. The final step runs `finalCheckCommands`, the list the review and fix laps run.
- Only `runVerify` decides pass/fail; `noopCommand` (an always-passing `Test:`) is warned about because it wedges the red gate.
### Requirements are the spec's contracts (extensions/pb/spec.ts, extensions/pb/build-start.ts)
- There is no requirements file, delta grammar or merge: a capability's durable rules live in the spec that changed them, approved through `approveSpec`'s `contractHash` (`contractText` excludes only Design and Decisions). `/pb:archive` keeps the approved spec; git keeps earlier versions.
- A changed contract outside the build pauses it (`approvalDrift`); the only re-approval is `/pb:build`'s, and it shows the changed blocks for a confirm first (no UI: it proceeds and says so), so no second copy can drift from the spec the human read.
### Fresh sub-agent runs (extensions/pb/runner.ts, extensions/pb/review.ts, extensions/pb/progress.ts)
- Explorer, trier and cartographer get `bash` and are reverted by `revertFreshRun`; the spec reviewer and dry-run keep their revert as a belt (they have no shell any more); the **code review** names paths that changed while it ran instead of reverting, because a file changed in that window is as likely the human's.
- The reviewer is the one watched session; the adversarial pass is a `runFresh` background process on the same frozen brief, named in the result, and its tokens are recorded as `review-usage` so `/pb:stats` counts what the review cost.
- The claim check is a fresh run too: `runClaimCheck` passes `maxConcurrent`, `--no-mcp` and a `tools:` list naming `report_findings`, like every other fresh role.
- A fresh run's live display is `freshProgress` (progress.ts): one widget per role (step, time, tokens from `onUsage`, the last five `describeCall` actions, the session file from `onSession` once Pi has written it); a new role spreads its `hooks` into `runFresh` and calls `stop()` in a `finally` rather than drawing a widget of its own.
- Never post a run's activity into the conversation: it would become every later turn's context.
- All fresh runs funnel through `runFresh`, whose FIFO slot cap is `config.maxConcurrent` (the project's `config.json`, else the user-level pb config merged in by `Store.config` under Pi's agent dir) overridable by `PI_PB_MAX_CONCURRENT`; new roles must pass the cap through or they bypass it.
- A fresh run can carry `timeoutMs`: the clock starts once it holds a slot (queue time is not probe time), expiry kills the whole process group like an abort, and the result says `timedOut` so a caller can name the limit. `pb_try` passes `config.probeTimeoutSec` (default 900 s, `0` = no limit); a trier's `bash` has no default timeout of its own, so this is the only bound on a runaway probe.
- Pi's own `bash`/`powershell` calls have no default timeout either: hooks.ts's `tool_call` guard sets `input.timeout` to `config.commandTimeoutSec` (default 1800 s; `0` = off), keeping a shorter timeout the model asked for and clamping a longer one. Pi applies no validation after a hook mutation, so the value must stay a positive finite number.
- The build task prompt and the `/pb:fix` seed tell the model to stop and report a timeout instead of retrying it.
- A fresh role names its reporting tool in `tools:` (`--tools` replaces the whole selection, **extension tools included**, so an unnamed `report_findings` / `report_verdicts` / `report_map` is never declared and the run can never report). `test/mock-pi.mjs` refuses calls to tools `--tools` does not name, because the mock otherwise cannot see this class at all. (security)
- Fresh runs also pass `--no-mcp` (Pi 1.0.4+, gated on the exported `VERSION`): MCP is a built-in extension `--no-extensions` does not stop, so the user's servers would otherwise be spawned — and since 1.0.4 their tools kept by `--tools` — inside a process that is meant to see only the brief. (security)
### Stats and the machine report (extensions/pb/stats.ts, extensions/pb/report.ts)
- Events are the only source: a `review` event stores `p` (the **post-verification** P0–P3 tally) and `dismissed` as a count, a `fix` event stores fixed/skipped title lists. `/pb:stats`'s `Precision` line derives from them — no per-finding identity is stored anywhere, so a single finding cannot be tracked across laps without an event-schema change.
- The spec phase is measured from its events: `spec-review` and `spec-check` carry the fresh run's tokens and cost (`runUsage`, runner.ts), `spec-fix` the lap's settled items, and `summarize` folds them into `Summary.spec`, shown as the card's `Spec` line and as `stats.spec` in the report. These numbers are what a change to the evidence rules is judged by.
- A repair lap's own session is counted from its `lap-usage` events (phase `spec-fix`); a `/pb:fix` lap's, phase `fix`, is `Summary.fix`.
- `REPORT_SCHEMA` (`extensions/pb/report.ts`) is one document for `/pb:status --json`, `/pb:stats --json` and `pb-report`; `extensions/pb/report-cli.mjs` is that binary, declared in `package.json` `bin` rather than by the extension. A key leaves the document only with a new schema id.
### Config (extensions/pb/store.ts)
- `sanitizeConfig` is the one judge of a setting's value; `configProblems` only reports where it overruled the file (unknown keys against `CONFIG_KEYS`; replaced values; user-level keys other than `GLOBAL_CONFIG_KEYS`; unparseable JSON), shown at startup and by `/pb:status`. A new setting goes into `DEFAULT_CONFIG` or `CONFIG_KEYS`, or every user who sets it is told pb ignores it.
### The project map (extensions/pb/map.ts, extensions/pb/map-flow.ts)
- The map's size rule is per bullet (`MAP_BULLET_CHARS`, `longBullets`): over-long bullets go back through the one repair pass with unresolved paths and the budget, and the result counts what is still long. `MAP_TOKENS` is a sanity bound, never a reason to drop a still-true invariant.
- The map is one text to the cartographer and several files on disk: `splitMap` keeps the whole-project headings (and the `### Area notes` index pb writes) in the root AGENTS.md and puts each area heading in its folder's AGENTS.md under the same markers; `readMap` reassembles them, so the cartographer, the checks and `/pb:map undo` see one map. (security)
- `areaDir` is the only place a heading becomes a folder (it must exist inside the project by its real path, not be the root, dot-named, `node_modules` or git-ignored), and `areaNotes` re-checks every index line with it, since anyone can edit the root file. `mapDefect` covers every file a write touches, so nothing is written when one section's markers don't resolve. (security)
- Handouts name area notes through `specRef` (kit.ts: the folders the spec cites) and the review brief through `areaNotesFor` over the changed files; a new handout that carries `specReference` goes through `specRef`.
- The map check (`MAP_CHECK_SYSTEM`, read-only, `report_verdicts`) reads the code behind the new or changed bullets (`changedBullets`, at most `MAP_CHECK_LINES`) before the repair pass; contradicted lines go to that pass with their evidence, and one kept word for word is a dialog warning. No verdicts is said, never read as a pass.
- Whether the map works is measured, not assumed: `MAP_FINDING_RULE` (prompts.ts, shared word for word by the reviewer and the abuse pass) tags a finding `map: "stated" | "wrong"`, and parsing keeps only `MAP_TAGS` (`mapTagOf`, store.ts), so model text never mints a tag. The `review` event records `mapCounts`, and stats read the **first** review's tally.

- The "needs a look" dialog applies the proposal when unanswered (a wrong map costs `/pb:map undo`, a discarded one the whole run) and posts what it was flagged for. A dismissed proposal is kept (`Store.saveMapProposal`, `.pi/pb/map-proposed.json`, with the map it was made against as `base`); `/pb:map apply` writes it only while `readMap` still equals that base, so it never overwrites a map changed since. A deliberate keep or any successful map write drops it.
### Standards (extensions/pb/standards.ts)
- pb's machinery is generic; its standards presets (java, rust, vue) are opinionated on purpose, because they are offered (never imposed), written where the human reads them, and replaced by a same-named template in `templatesDir()`. What a preset assumes is `Template.assumes`, named by `presetNote`. Presets carry no version pins (they rot) and no facts about one team.
- A section is composed, never a fixed text per stack: `backend(database, stackLines)` = core, the `DATABASE` part when `usesDatabase(cwd)`, the re-read, then the stack's lines last, so a shared core stays a prefix of every stack's own and `offerStandards`' "a shared section is enough" check keeps working. A shared section must never carry stack or database rules.
- Every project manifest pb reads for detection (package.json, Cargo.toml, pom.xml, Gradle, go.mod, Python) goes through `extensions/pb/manifest.ts` (`readManifest`, `readJsonManifest`, `packageScript`): non-blocking open, regular files only, at most 1 MB — the project's files are untrusted input, and a pipe planted under a manifest's name must not hang a command. Never `readFileSync` a manifest.
### The build's lifecycle (extensions/pb/phase.ts)
- Every phase change goes through `phase.ts`: `enterStep` (a step starts or resumes: `building`, `current`, pause cleared), `pauseAt`, `finishBuild`, `markReviewed`, and `nextPhase` for a (re)start in `initBuildProgress`. `PHASE_TRANSITIONS` is the whole lifecycle, and an impossible move throws rather than leave a record no command can continue.
- Never assign `p.phase` elsewhere (the reads that migrate a legacy `"checking"` are data repair, not moves); `restorePhase` (`/pb:undo`) is the one move outside the table, because the row is the authority.
- What follows a passed step is `nextStep` (task → one coherence pass when `needsCohere` → final check unless the step just ran the suite and no project check remains → done); `advanceAfterCheck` only executes the answer.
### Where you are, what's next (extensions/pb/next.ts, extensions/pb/kit.ts)
- `whereNext` (one spec) and `whereHere` (this session) are the **only** derivation of state and next step, computed from progress, events and the text on disk, never stored. The footer (`refreshWhere`), `/pb:status`, `/pb:help` with no topic, the startup greeting and the alt+n shortcut all read it; a new phase or verdict is added there, never as a hand-written next step in one place.
- `refreshAfterCommands` (index.ts, installed before any module registers) wraps every pb command so the footer refreshes when it returns — Pi has no "a command ran" event; `turn_end`, `agent_settled` and `session_start` refresh it too. The greeting fires only on `startup`: pb's own switches back from a review or fix lap arrive as `resume`.
- Argument completion: Pi replaces the whole argument text with the chosen value, so `fixCompletions`/`specFixCompletions` build the full `<spec> <n>...` (the spec is written in when it was inferred, so the command resolves the same one).
### Planning's role (extensions/pb/prompts.ts, extensions/pb/hooks.ts, extensions/pb/kit.ts)
- The planner's role, stance, whole-system walk and ledger rule are `PLANNER_ROLE`, set as the `pb_planner` system-prompt section by hooks.ts's `before_agent_start` on every run of a session in `planningSessions()` (with `extra.plan` appended), and removed on any other run. Never paste the stance into a first message: a rule given once fades over a long discussion.
- `checkpointSummary` (the reset) carries the spec, not the stance; the first messages (`planPrompt`, `continuePlanPrompt`, `approachPrompt`) carry only the task, the investigation steps and the reply shape.
- The planner's model and thinking floor (`config.planner`, default floor `"high"`) are applied by `applyPlanner` when planning starts (`/pb:plan`, `/pb:deps`) and handed to a continued plan's new session through the carry. What planning changed is stored on disk in the session's planning record (`PlannerSettings`, `store.setPlannerSettings`), so a restart keeps it.
- `liftPlanning` puts back only what is still as planning set it (`restorePlanner`), so a level you chose mid-planning is kept; `plannerSettings` is the pure decision.
