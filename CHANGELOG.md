# Changelog

## Unreleased

pb now covers a change from plan to commit with the next step always on screen, proves more of its own claims (a task's test, a fix's test, the checks before a review), keeps its probes away from production, and spans a backend and its frontend in sibling repositories. Laps run in sessions of their own, the project map is split into area notes and checked against the code, and one rule — build for the needs you have, cleanly — replaces "smallest change" everywhere.

**Behaviour you will notice**

- Phases no longer post a commit message: run `/pb:commit` when you want to commit.
- A planning session refuses shell commands that write to a database, cluster, cloud or API, and edits inside a sibling repository.
- `/pb:build` refuses while another spec is building in another session of the same working tree.
- With the default `taskChecks: "end"`, a task that proved itself red has its own `Test:` run when it reports done: builds take a little longer and prove more.
- `/pb:review` runs the project's checks and each task's `Test:` first; a red one caps the verdict at UNVERIFIED.
- The standards wording changed (no overengineering instead of "smallest", no version pins): run `/pb:standards` in a project to update its section.
- The first `/pb:map` or archive after upgrading splits the map into area notes, shortens long bullets and checks every new line against the code: expect one longer, costlier run. `/pb:map undo` reverts it.
- `null` for `verify`, `build` or `lint` now turns that command off, as documented (it meant `"auto"`).

### Planning

- **Planning changes nothing outside the machine.** In a planning session, a shell command that would write to a database, a cluster, a cloud or an API is refused (reads still work), and edits inside a sibling repository are blocked like edits to the project.
- **Every answer reaches the spec.** What you answer while planning is kept with the planning session, and `/pb:spec` lists it for the writer to put in Decisions, so a long discussion or a reset can't lose one.
- **`pb_ask` is easier to answer.** Independent questions come in one call, "Question 1 of 3", with one notification; if one goes unanswered in time, the rest wait in the chat. A question where several options apply is a checklist. A typed letter reaches Pi as the option it names ("B — events"), and a recommendation is marked however the model wrote it (its letter, or part of its text).
- **Planning covers time.** The planner's walk now includes time zones and day boundaries, for a change that handles time; the spec checks ask a time to name its clock or zone. Time handling is a classic source of bugs that starts as a planning decision.
- **`/pb:approach` reads the area notes** like every other planning prompt.
- **`/pb:deps` is a full dependency review.** It now gets planning's frame (the investigation steps, the background baseline, your standards, and the What-now block) and asks what an upgrade review needs: known vulnerabilities and whether your code reaches them, deprecated APIs you call, the runtime and toolchain against their supported versions, and versions a host pins. It names your stack's own read-only commands for outdated packages and advisories, and forbids installing or updating anything into the project. A breaking change cites its changelog entry and your call site. The reply groups the upgrades into changes you would merge on their own, in order, and asks which to do; `/pb:build` writes one spec per chosen change.

### Specs and the spec review

- **A P1 from the spec review is your call before T1.** When the review of the text about to be built raised a P1, the build shows it and asks: build anyway, repair first (`/pb:spec-harden`), or stop. Before, a P1 was posted and the build started in the same breath; a pass recorded earlier (by `/pb:spec-review` or the last review of `/pb:spec-harden`) was reused without showing its findings at all. In two real builds, a known P1 went unaddressed and code review found the same bug later, at three times the cost. Only a P0 still blocks; a restart or resume of an approved text is not asked again; with no UI the build goes on and says so.
- **Each spec-review finding names the check it fails**: Claims, Values, Proof, Coverage, Reach, Consistency, Overengineering (the writer's checks), Evidence or Other. The finding line shows it (`[P1 · Values]`), and `/pb:stats` counts findings per check (`by check …`, and `stats.spec.byCheck` in the report). That shows which of the writer's checks still let problems through.
- **A spec can cite a sibling repository.** A change that spans a backend and its frontend can cite `../<repo>/<path>:<line>`, and the write gate checks that line exists like any other. Before, only quotes were possible, and the claim check then flagged them. Only a regular file one folder up from the project counts: never a path that climbs further, a link out of that folder, or anything dot-named (`.env`, `.ssh`, `.git`).
- **Changes that span two repositories.** A spec names the sibling repositories it also changes (`Also changes: ../frontend`), and pb covers them as it covers the project: the build records where it starts there, every undo point snapshots them and `/pb:undo` puts them back, the review's diff and changed files include them, and `/pb:commit` commits their files in each repository with the same message. A spec naming a sibling that isn't a git repository beside the project is refused before it's built.

### Repair laps

- **Repair laps run in a fresh session.** `/pb:spec-fix` and `/pb:spec-harden` used to run each lap inside the planning conversation, where the planner role was active, the whole discussion was carried along (one real session had reached 248k tokens), and lap transcripts piled up. Each lap now gets a session of its own, `spec-fix: <spec> · lap N`, seeded with the spec and its worklist and running on the model the run started from; pb brings you back after it, and the results land in your session.
- **Hardening keeps a lap for the confirming review.** `/pb:spec-harden` used to run a claim check after every lap and give each round of claims a lap of its own. In a real run, two laps went to three minor claims, and the confirming review's P1 then found the lap budget spent. Now the claim check runs once, after the first lap. Its claims get a lap only while one stays free for what the confirming review finds, and claims no lap took are listed for you. One check instead of three also saved about half an hour in that run.
- **A repair lap edits by section and checks its own work.** A lap now changes the spec section by section with `pb_update_spec` instead of rewriting it whole, and before reporting it runs the same spec checks as the writer over what it changed. In the real run, one lap settled a claim and wrote three new unsupported ones, and the spec grew 17% despite the instruction to keep its size.
- **P3 polish is left to you in hardening too.** `/pb:spec-harden` now repairs P0–P2, like `/pb:spec-fix` already did; name a P3's number to `/pb:spec-fix` to repair it. Polish adds text, and more text gives the next review more to flag.
- **A lap never waits on a question forever.** Since laps run in sessions of their own, a `/pb:spec-harden` or `/pb:fix` lap that called `pb_ask` opened a dialog with no timeout, so an unattended run could hang. A fix lap and a hardening lap now never ask (a fix reports the finding as skipped, a hardening lap parks the question with its recommendation); a manual `/pb:spec-fix` lap still asks, with the timeout.

### Building

- **One build-start screen.** `/pb:build` used to ask one dialog per concern: an unbuilt dependency, a red baseline, the spec review's P1s, where to build. It now shows them all on one screen after the spec review, with one choice: build here or fresh, repair first, or stop.
- **One build per working tree.** `/pb:build` refuses while another spec is building in another session right now, since both builds' undo points, review, checks and commit would see each other's files. Another spec whose build left uncommitted files (paused, stopped, or done but not committed) is named on the build-start screen, with `/pb:commit <it>` as the way out.
- **pb runs a task's own test when it reports done.** With the default `taskChecks: "end"`, pb watched a task's `Test:` fail before the change but never ran it afterwards: "it passes now" was the model's word until the final suite or the review. A task that proved itself red now has its `Test:` run by pb on `pb_task_done`, and the handout stops asking the model to run it first. The final step's commands come from the same list the review and fix laps run.
- **No overengineering, which is not the same as "simplest".** pb asked for the smallest change in several places (the build's craft rule, the planner, the Simplicity standard), which can steer a builder toward a quick fix that leaves debt. One rule replaces them, word for word in the planner, the spec check, the builder and the reviewer: build for the needs the change has, not ones it might have; every added part (an option, a layer, an abstraction, an endpoint, a dependency, a job, a cache, a stored field) traces to a stated need and is something more to secure; within those needs, the cleanest design wins over the smallest. The spec review gains an Overengineering check; the code review makes an unneeded part P1 when it adds attack surface; the Vue preset gains the rule too.

### Review and fixes

- **A fix lap follows the builder's craft rules.** It fits the codebase (conventions, extending helpers instead of copying them) and makes the cleanest fix within the findings, not the smallest; before, only a build task was told so.
- **A follow-up review sees a fix made only in a sibling repository.** "Nothing changed since the last review" now checks each sibling too, from its snapshot at the last review; one with no snapshot is never skipped.
- **A review never passes over a red check.** `/pb:review` now runs the same checks as the build's final step (lint and extra checks included, not just the suite), and each finished task's `Test:` command, before the reviewer starts. Before, the result only went into the brief, and the verdict came from the reviewers alone, so a review could say PASS over a failing suite. Now a red check caps the verdict at UNVERIFIED and names the command.
- **The reviewer can cite test runs.** The reviewer has no shell, so an acceptance line that needs a test run stayed "not verified" even when its test passed: a real follow-up review ended UNVERIFIED on exactly that. pb now runs each finished task's `Test:` and puts the result in the brief, as evidence the reviewer can cite. A command that chains shells or reaches the network is not run, as at the pre-approval dry run.
- **The review brief lists the dependencies a change adds,** read from the manifests before and after (package.json, Cargo.toml, go.mod, pom.xml, Gradle, pyproject.toml, requirements files), in the project and its sibling repositories. Each needs its reason in the spec.
- **pb checks a fix itself.** After each `/pb:fix` lap, pb runs the reproducing tests the lap saw fail (they must now pass) and the same checks as the build's final step. Before, "Fixes complete" was only the lap's own word, and you found out at the next review. A red check means the lap's fixes don't count: the next lap gets the failure, and with no lap left the run stops and shows it.
- **A fix is proven like a build task.** For each finding that changes behaviour, the lap writes a test that reproduces it and pb sees it fail (`pb_fix_red`) before the fix; `pb_fix_done` refuses "fixed" without that proof, unless the lap says why no test can show it (a doc line, a config value). This replaces the old instruction that the task's own `Test:` line must fail, which it never could: it passed at build time.
- **A finding is a class.** A fix lap now looks for the same defect across the whole change and fixes every instance, and checks any rule it writes in a doc against the code. In a real follow-up review, 3 of 4 new findings were the fixed bug's siblings or a doc rule the lap wrote wrong.
- **A fix keeps the spec true to the code.** A `/pb:fix` lap now updates the spec's Design and Decisions when its fix changes the behaviour they describe. Before, a lap was told to write nothing under `.pi/`, so after a fix the spec still described the old behaviour, and the follow-up review spent a finding saying so. The lap can change only those two sections of its own spec: neither is part of the approved contract, so nothing needs re-approval. A finding that needs the Goal, Contracts or Acceptance changed is still reported as skipped. This is enforced by the spec tools, not just the prompt: before, nothing stopped a fix lap from rewriting any spec.
- **Each fix lap is an undo point** (`/pb:undo fix1`): files and spec as they were before the lap.
- **The follow-up review is offered** when every finding is fixed and the checks are green; choosing it puts `/pb:review <spec>` in your editor.
- **Fix reports are read by finding number**, so two findings with the same title are never resolved together.

### The project map

- **Area notes: a session reads the map it needs.** The map's whole-project headings stay in the root AGENTS.md, which every session reads; each area heading names its folder and lives in that folder's own AGENTS.md. Each build handout names the notes for the folders its spec cites, and the review those for the files it changed, so a frontend task no longer carries the backend's deploy rules. Other agents working in a folder find its notes there too. A heading naming no safe folder inside the project stays in the core.
- **New map lines are checked against the code before they're written.** A fresh read-only check reads the code behind each new or changed line. A line it contradicts goes back to the cartographer with the evidence; one kept word for word is put to you. Agents read the map as instructions, so a wrong line was worse than a missing one.
- **The project map is limited per bullet, not in total.** Each bullet is the rule, where it is enforced and the test that proves it, in about two sentences (400 characters), with the mechanism left to the code. Longer bullets go back to the cartographer once to be shortened, never dropped, and the result counts any still too long. The 20,000-token total is only a sanity bound: a project with more invariants gets more lines, never fewer rules.
- **Is the map working? The reviews say.** The code reviewer and the abuse pass mark a finding that breaks a rule the map states, and report a map line the code contradicts as its own finding. The post shows both on each finding; `/pb:stats` (a `Map` line) and `/pb:stats compare` (a `map` column) count them from each spec's first review.

### Commit, undo and archive

- **`/pb:commit`: commit when you choose.** The build completion, every review message and the archive result no longer post a "Commit message, to paste" block (it repeated the same text into the conversation at each phase, even after a review that asked for changes). `/pb:commit` commits the work whenever you run it: after the build, the fixes, the review or the archive. It opens an editor with the message and the uncommitted files, git-style: edit the message, delete a file's line to leave it out, clear the message to cancel. The message is built from the spec, not by a model: the first commit carries the title, goal and tasks, a later one the review fixes since, a map-only commit after archiving what the map gained. It commits explicit paths only (never `git add -A`, never pb's state or the spec), leaves the rest of your staging area alone, runs your hooks, and refuses while a build or a repair lap is still writing files. When nothing changed since the last commit it says so and stops.
- **`/pb:undo` can keep your edits.** It restores the whole tree, so a file you edited after the undo point went back too. When a file differs that no finished step changed, it now names those files and asks: restore all, or only what the finished steps changed.
- **Archiving asks when work is left.** `/pb:archive` used to archive any built spec silently, even one never reviewed or with open findings, which then left `/pb:fix`'s reach. It now asks first and names what is owed; with no UI it archives and says so. A name that isn't a spec name is refused with a clear message.

### Exploring and probing safely

- **`pb_explore` and `pb_try` can't reach production.** Both ran with an unrestricted shell and your whole environment, guarded only by their prompt. Now:
  - the explorer's shell runs read-only inspection commands only (ls, find, cat, head, tail, wc, rg, grep, git status/log/diff/show), enforced: a database client, a network call or a script is refused;
  - a probe's commands that write to a system outside this machine are refused (database writes, cluster, cloud and infrastructure changes, HTTP writes, remote shells, pushes);
  - both shells run without database, cloud and cluster credentials, and the common tools' credential files point at nothing. Pi's own process keeps its model keys.

  Fix laps now carry the production rule too.
- **No genuine long command is cut short; a stuck explorer is.** The project's own long commands (suite, compile, lint, extra checks, every `Test:` line) get the larger of `commandTimeoutSec` and `verifyTimeoutSec` wherever they run; inside a probe, no command outlasts the probe. The explorer, which had no limit at all (real runs reached 3.5 hours), now stops after `explorer.idleSec` (10 min) without progress or `explorer.timeoutSec` (30 min) in all, and each of its commands after 2 minutes. Inside both tools, the per-command limit now applies too: before, it was only enforced in pb's own sessions. A stopped command or run says which limit fired and how to raise it, and each tool's brief states its limits up front.

### Knowing where you are

- **You always know the next step.** The footer now shows `pb · <spec> · <state> · next: <command>` at every stage, from planning to archive, and refreshes after every command and turn; the terminal title carries the spec and its state. Before, only a running build showed anything, and a "What now" block scrolled away. **alt+n** puts the next command in the editor. `/pb:status` gives every spec its next step, `/pb:help` with no topic opens with where you are, starting Pi on work in progress says it once, and `/pb:archive` ends with the next step too. All of them read one derivation of where a spec stands, so they can't disagree.
- **Numbers complete.** `/pb:fix` and `/pb:spec-fix` complete finding numbers with each finding's priority and title, and `/pb:undo` completes checkpoint ids with what each undoes: no scrolling back to find them.
- **pb says when it is waiting for you, and what it did when you didn't answer.** While a dialog is open the footer reads "pb · waiting for your answer"; a choice that times out posts the default pb took.
- **Sessions are easier to find in `/resume`.** Fix laps are named `fix: <spec> · lap N` and are all children of the session that ran `/pb:fix`; a planning session that starts building is renamed `build: <spec>`.

### Standards, stats and config

- **pb's standards presets say what they assume.** The Java, Rust and Vue sections are opinionated on purpose; the offer and `/pb:standards` now name what each one assumes (the Vue one: the backend decides every rule, an HttpOnly session cookie with CSRF tokens, RFC 9457 problem details, TanStack Vue Query, Bootstrap, pnpm) and where your own goes instead. They no longer pin versions ("Java 25", "Vue 3.5", "TypeScript 6", "edition 2024"), which went stale and contradicted their own Dependencies rule, and the Vue comments rule no longer describes one team.
- **Lap costs are counted.** Repair laps and `/pb:fix` laps run in sessions of their own, whose turns were counted nowhere. Their tokens and cost are recorded now: a repair lap's in the spec phase, a fix lap's as `Fix laps` on the card and `$fix` in `/pb:stats compare`.
- **`/pb:stats compare [n]`** lines up the last n specs phase by phase: what the first spec review and the first code review found, the repair and fix laps, the first-try rate and what each phase cost.
- **Config mistakes are named.** A mistyped key (`comandTimeoutSec`: did you mean `commandTimeoutSec`?), a leftover one, a value pb replaces with its default, a setting the user-level file isn't read for, or a config that isn't JSON is listed at startup and in `/pb:status`; before, each fell back to the default without a word. And `null` for `verify`, `build` or `lint` now turns that command off, as documented: it used to mean `"auto"`.

### Internals

- **`flow.ts` is five files, by role.** The 2,600-line module that held the spec tools, the spec review, the repair laps, the build loop and `/pb:build` is now `spec-tools.ts`, `spec-review.ts`, `repair.ts`, `build-loop.ts` and `build-start.ts`. Every block moved verbatim; no prompt and no behaviour changed.

## 1.39.0

- **Planning is led by a senior engineer, for the whole conversation.** What planning asks of the model is now a role, set in the system prompt on every turn of a planning session. Before, it was a paragraph in the first message: it faded as the discussion grew, and a checkpoint reset dropped it entirely. The role:
  - **Who it is:** the senior engineer who owns the change end to end, from the need behind it to running it in production; its job is the best plan for what you need, not agreement with your first idea.
  - **Problem before solution:** it states the goal and how you'll know it worked, and challenges the request itself when it deserves it (the need behind it, an existing solution, the simplest thing that would work). A request that is already right gets one line. The first reply now opens with a **Problem** section.
  - **Expertise counts as evidence:** a named practice, standard or documented behaviour, with its consequence here, now backs a pushback just like a `path:line`. Taste still doesn't.
  - **The whole lifecycle is walked, in proportion:** a small change touches one or two of these lenses.
    - users: what they see on success and failure, accessibility and languages for a UI;
    - design: where it belongs, what it couples, what generality nobody needs;
    - data: ownership, existing records and API clients, personal data and retention;
    - security: access, leaks, new dependencies;
    - input and state;
    - verification: how it will be proven, what no test shows;
    - operations: rollout, migration order, rollback, how you'd see it fail in production, latency and cost at scale.

    Legal, compliance and licensing questions are flagged for the right person instead of answered.
  - **A ledger:** after the first reply, every answer ends with Decided and Open. When you overrule it without new evidence, it records your choice with its objection and the risk, then stops arguing. `/pb:spec` writes that ledger into the spec.

  The first planning message shrinks from about 850 to 600 words. Your `extra.plan` instructions move into the role, so they last as long as it does.
- **Planning thinks harder, and can run on its own model.** Starting planning raises the session's thinking level to at least `"high"`, and to `planner.model` when one is configured (`"planner": {"model": "provider/id", "thinking": "xhigh"}`). Ending planning puts both back, unless you changed them yourself in the meantime. What planning changed is kept with the planning record, so a restart doesn't lose it, and a plan continued in a fresh session carries the same settings.

- **One evidence rule, and only for claims that matter.** The spec format, the spec reviewer, the claim check and a repair lap now judge evidence by the same rule, word for word:
  - **Only load-bearing claims need evidence**: those that would change the build if false (a number or bound, what this repository does, how an outside service behaves). Before, every observable value and every number needed a citation, while the claim check only looked at load-bearing ones; a spec written to the stricter rule grew, and a bigger text gave a fresh review more to flag.
  - **A test can be the evidence.** A value this change itself defines, such as a new status code, is proven by the Acceptance line that pins it, since its red test checks it. A claim about code or a service that exists today still needs its `path:line` or a probe, because a test written from the same belief would pass even if the belief were wrong.
- **An assumption is written one way, and you see every one.** A claim nothing settles yet is tagged `assumed: <what would falsify it>` right after it. Before, the writer was told to write "Assumption" entries in Decisions while repair laps used the inline tag, and only the Decisions form was read. So the assumptions a lap added never appeared in the "Settled without asking you" list shown before a build. One parser now reads both forms, and older specs keep working.
- **The spec phase is measured.** Spec reviews and claim checks record their tokens and cost. `/pb:stats` adds a `Spec` line per spec (reviews and blocks, findings P0–P3, claim checks and the claims they found, repair laps with what they applied, rebutted, parked and assumed, tokens, cost and time), and `pb.report/2` carries the same numbers as `stats.spec`. These are the numbers a later change to the claim check will be judged by.

- **The spec writer runs the spec reviewer's checks before writing.** One list, shared word for word by the writer and the reviewer, built from the findings real spec reviews kept raising:
  - claims about existing code are re-read at their line, not remembered from the discussion (the writer reads the lines itself; `pb_explore` only for what it can't place);
  - every new value has its unit, range, sign and empty case, and a time names its clock and what happens when the day changes;
  - each Acceptance line has a test that can fail before the change;
  - each Contract and each behaviour-changing Decision is pinned by an Acceptance line (a Decision no line pinned was the one bug that reached code review in the last real build);
  - the tests, callers, links and docs that assert the old behaviour are named, with a task to update each;
  - the sections agree.

  Fixed before writing, these no longer cost a review, a repair lap and a claim check each. The `Spec` stats line shows whether first reviews find less.
- **A rewrite says what it removed.** `pb_write_spec` and `pb_update_spec` now list every section, Acceptance line and Decisions entry the previous text had and the new one doesn't. A whole rewrite can no longer silently drop what a review lap added.
- **The planner's answers have a place in the spec.** Migration and rollback also covers rollout, how you'd see it fail in production, and what no test can show; Contracts include what a user sees when it fails. A reply that writes the spec no longer ends with the planning ledger: the spec is the ledger.

- **Rust projects get clippy, and auto-detected lint never stalls the first task.** `"lint": "auto"` now also detects `cargo clippy -q --all-targets -- -D warnings` for a Cargo project, after package.json's own `lint` script. Where lint gates a build is decided once, at its start:
  - **every task**, when you set `"lint"` yourself, or when the planning baseline ran the auto-detected lint clean on this commit;
  - **the final check only**, otherwise, with a notice saying why. A project with existing warnings then reaches the end of its build instead of failing T1 for debt it did not create.

  A restarted build keeps its gate, and one started before this release stays per-task.
- **No manifest read can hang pb.** Detecting the test, compile and lint commands, the project's stack and its database now reads package.json, Cargo.toml and the rest through one helper. It opens without blocking, reads regular files only and stops at 1 MB, so a pipe planted under a manifest's name can no longer hang `/pb:plan` or `/pb:build`. npm's "no test specified" placeholder still never counts as a command.

## 1.38.0

- **The build's lifecycle is one table.** `phase.ts` holds the phase transitions:
  - written → building;
  - building → paused or built;
  - paused → building;
  - built → building or reviewed;
  - reviewed → building.

  Every phase change goes through it, and an impossible move (pausing a finished build, reviewing a paused one) throws instead of leaving a record no command can continue. `/pb:undo`'s restore is the one named exception. What follows a passed step (the next task, one coherence pass, the final check, or done) is now a pure `nextStep()` that `advanceAfterCheck` only executes. Both are unit-tested without the simulated Pi.
- **The suite is split by area and runs in parallel.** The 8,600-line `pb.test.mts` is now one harness plus `plan`, `spec`, `build`, `review` and `core` test files. `npm test` runs `test/*.test.mts` and takes about 65 s instead of about 170 s; `verify-test` runs the whole suite unless given `--file`.
- **No dead imports.** About 780 unused imports and a few dead locals, left over from splitting `index.ts`, are gone, and `noUnusedLocals`/`noUnusedParameters` keep them from coming back. Two tests whose assertion could never fail (a regex returned from a `.some()` callback instead of tested) now test the note they name.

- **Every prompt has a snapshot, and prompt size is reviewed instead of capped.** `test/prompts.golden.test.mts` renders each prompt pb sends with fixed inputs into `test/golden/<name>.txt`:
  - planning, spec, task, coherence pass, retry, nudge and fix seed;
  - reviewer, attacker, verifier, spec reviewer, repair lap, claim check, explorer, trier and cartographer;
  - every tool's description and parameter schema.

  Each snapshot's first line is its word count. A change, direct or through a shared rule, fails the test until `UPDATE_GOLDEN=1 npm test` rewrites the snapshot, so it lands as a readable diff of what the model actually reads. The build-mechanics 1,300-character cap is gone: growth is a review question, not a number to squeeze under. The fix seed moved from `fix.ts` into `prompts.ts`, so every prompt is built in one place.
- **Prompts say each rule once.**
  - Five rules each had their own copy in several prompts; every one is now a single shared rule: the project-map reading order (4 copies), the production rule (5 copies, including `pb_try`'s description), the shell-timeout rule (task and fix seed), the planning investigation steps (plan and continued plan), and the spec-format bullets `/pb:spec` repeated.
  - The planning stance (`CHALLENGE`) keeps every rule in about half the words.
  - The Contracts guidance is a short paragraph plus one bullet per rule.
  - The structured-edit rule drops its pom.xml regex example.
  - Net effect, measured on the snapshots: plan −18%, spec −9%, finish-spec −5%, approach −14%, trier −22%. The continued plan grows by about 80 words because it now gets the full investigation steps rather than a condensed copy that had drifted.

- **Standards fit the project, and Rust has its own.** pb's standards section is now assembled from parts:
  - **A core every project gets.** It is stack-neutral and has a new **Simplicity** rule: no option, layer or abstraction without a second user or a stated reason, no near-copy of an existing helper, no code kept for a case nothing reaches.
  - **The database rules**, only for a project that uses a SQL database. Before, every project got them. They are detected from a driver or ORM in package.json, Cargo.toml, pom.xml, Gradle, go.mod, pyproject.toml or requirements.txt, or from a migrations directory.
  - **The stack's own lines.** Java 25 as before, and a new **Rust** part (detected from `Cargo.toml`): typed errors propagated with `?`, no `unwrap`/`expect`/`panic!` outside tests unless an invariant rules failure out, `unsafe` only with a `// SAFETY:` proof, newtypes for validated values, no blocking in async code and no lock held across `.await`, clippy and fmt clean.
  - A project with a database under a shared core section is offered its own section, since the shared one must not carry database rules. Manifests are read as regular files only, up to 1 MB, so a pipe planted under a manifest's name cannot hang the offer.
- **The reviewer looks for what the change could do without.** A new Simplicity lens reports an abstraction with one user, a near-copy of an existing helper (named), a check repeating what a type, constraint or earlier boundary already guarantees, and unreachable code. Each is a P2 whose fix is the deletion or the reuse. The reviewer is told that another guard is not the default fix and to prefer the invariant that makes it unnecessary, so a review pushes toward less code as well as safer code.
- **Quality feedback reaches the task that needs it.** Three changes aimed at the code a build writes:
  - **Lint runs after every task**, not only at the end. A style, unused-code or type finding fails the task that caused it while its context is still loaded, instead of piling up for one final repair. The final step skips lint when it follows a passed task directly, and re-runs it when the final check is retried.
  - **The task handout says how to write the code**: match the conventions of the code that already solves the same problem (the spec's Findings name it) but never copy its flaws (where that code falls short of the standards, the new code meets them and the old pattern is reported as open), extend a helper rather than adding a near-copy, and make the smallest change that meets the Acceptance lines. Before `pb_task_done`, and before a fix lap's `pb_fix_done`, the agent re-reads its own diff for duplicated or dead code, debug output, unclear names, and comments that restate the code or tell its history.
  - **A later task sees what the earlier ones declared.** Builds reset between tasks, so the handout's "Already done" list now shows each file with the names its task added (`src/orders.ts [cancelOrder, OrderState]`). The names are read from the task's checkpoint diff for TypeScript/JavaScript, Rust, Go, Python, Java, Kotlin, C# and Scala, with test files skipped.

- **A `Depends on:` note no longer breaks the build, and an archived dependency counts as built.** The header parser took the whole line (`tempo-gtfs-live-trains — implemented and on HEAD; ...`) as the dependency name, so `/pb:build` called `store.progress()` with that phrase and `specDir()` threw `"not a valid spec name"`. The parser now takes the first token as the name and only allows a note after a dash or in parentheses. Reads (`store.progress`, `store.checkpoints`) now see nothing for an invalid name instead of throwing — writes keep the refusal. And the build gate checks `store.finishedPhase()`, which looks at the live record then the `.pi/pb-archive/` record (matched on the archived progress's own spec), so a dependency that was built and archived no longer warns "isn't built yet". A live rewrite of the same name starts over rather than inheriting the archived phase.

- **A shell command cannot run for hours.** Pi's `bash` tool has no default timeout, so an agent's unbounded loop can hold a session indefinitely: a Java probe that rebuilt a 2 MB input for every candidate length ran for 94 minutes in a `/pb:fix` session before the human noticed. Two bounds are new. Every `bash`/`powershell` call in a session carrying pb is capped at `commandTimeoutSec` (default 1800 s, `0` = off): the `tool_call` guard sets `input.timeout` before Pi runs the call, keeps a shorter timeout the model asked for, and clamps a longer one; the build's task prompt and `/pb:fix` tell the model not to retry a timeout but to stop and report it, so the cap reads as a limit to raise rather than a transient failure. And `runFresh` accepts a `timeoutMs` for the probes it spawns: the clock starts once the run holds a concurrency slot (queue time is not probe time), expiry kills the whole process group, and `timedOut` lets the caller name the limit rather than report a user stop. `pb_try` passes the new `probeTimeoutSec` (default 900 s, `0` = no limit) and its error tells the planner to bound the rerun; the trier's prompt also requires sizing inputs and wrapping anything that could hang in `timeout`.

- **The project map's cartographer reads, it doesn't re-run.** Its shell is now read-only by instruction — `git`, `rg`, `ls`, `cat`, `head`, `tail`, `find`, `wc`; no builds, tests, installs, servers, network calls or scripts — so a map update can't spend the run re-measuring the project. The prompt also bans snapshots (current version ranges, counts, inventories, pass/fail or measured results) in favour of the durable rule; keeps secrets and personal data out of AGENTS.md; writes routes with their verb and outside-repo paths as prose, so the path check stops flagging them; keeps every still-true line verbatim and reports an empty change list when nothing changed; and has the cartographer read the project's standards before naming a pattern or a gap, not restate them. The map's headings now fall into two kinds: the whole-project headings (`Security invariants`, `Layout`, `Tests + build`, `Docs`, `Known gaps`) carry no path and are read in every session, while every other heading is an area heading with its path prefix, so a session reads only the areas covering its paths. The planner, explorer and trier say the same thing.

- **A long review list is repaired by the model, not typed by you.** A spec review that returns fifteen P1/P2 findings used to mean reading every one and editing the spec by hand — and the pass after that fix found fifteen more, because a fresh reviewer reasons to new subjects instead of re-listing what you fixed. Three doors now do the clerking, and none of them decides for you. **`/pb:spec-fix [name] [ids]`** runs one repair lap in the session that owns the spec: it works only the findings recorded against the exact text on disk (`recordedFindings`, numbered as the review showed them), and for each it may do one of four things — run the probe itself and write what it measured into `Findings`, delete the claim, decide it in `Decisions` with the alternative it rejected, or tag it `assumed:` with what would falsify it — plus a written rebuttal with a `path:line` citation when it is sure the finding is wrong. It holds the ordinary spec pen (`pb_write_spec`), so the format gates and your standards still bind what it writes, and its probe (`pb_try`) writes nothing. **A claim check** then reads the new text with one narrow question — which load-bearing claims still carry no evidence and no `assumed` tag — because that is the fact that makes an unattended repair safe to leave running; new subjects stay the spec reviewer's job, and the pass records `spec-check`, never `spec-review`, so it cannot satisfy the build's review gate. **`/pb:spec-harden [name]`** sequences it: plan, one reviewing pass if the text has no verdict, lap, check, one confirming review, one last lap, digest — capped by `specFix.maxLaps`/`specFix.maxReviews` (3 and 2). The stop rule is facts it can check, not silence: a fresh full pass never runs out of subjects, so "no findings" would never stop, and the run adds no lap once the claim check and the confirming review find nothing, when a lap changed nothing, or when a budget is spent. What it would not decide it asks you once, each question with the recommendation that runs unattended; the lap that never reported stops and says so; a check that reports nothing is an error, not a clean bill; a lap left by a dead session is dropped, not obeyed; every lap is a `/pb:undo` point. `advanceSpecFix` is the only step-forward, so the manual and the automatic door share one sequence, and `Progress.fix` (which session may report, whose turn is owed) is the whole authority.

- **The repair flow cannot lie about its own result.** Five gaps are closed: a lap's report must account for every number its brief showed — a partial report is refused naming the missing ones, and parked or assumed items carry the number they settle; `/pb:undo` takes a whole repair lap back — each lap opens an undo point holding the spec text and phase it had before (`lap1`, `lap1-2`…, unique across runs), the spec is restored from that row through the same drift guard as the files (a spec edited while the question was open is named, never clobbered), and the phase and any open lap come back with it; a repair lap can write only its own spec — no shell, no edit/write, any other name refused; a review that reports nothing never reads as a pass — `/pb:spec-harden` stops instead of declaring the text hardened when the confirming review is silent or the text changed under it, the digest claims only a verdict that exists on the exact text, and a manual `/pb:spec-fix` stops at its claim check (only the driver chains another); and the digest no longer claims approval it didn't earn — with claims left standing, the evidence line says so instead of "it decided everything it was shown". Also: an unconfigured claim check runs at `low` thinking rather than the session default; a lap is never handed a `file:` anchor that doesn't resolve — it's named as unverified in the brief instead; two open laps can't coexist in one session (`openRepair` refuses a second while another is live there, a dead one is dropped); headless `/pb:spec-review` with several ready specs refuses and lists them instead of judging an arbitrary one; `/pb:spec-review --fresh` pays for a second pass at the same text instead of reusing the recorded verdict; and the review that passes with advisory findings names the door that works them through — both in the report and in the after-spec tip (`/pb:spec-fix`, `/pb:spec-harden`).

- **The spec-harden help says what a lap does.** Its opening summary packed the four repair moves and the stop rule into two run-on lines, and called a clean pass "no verdict" because the pass had no findings. It now names the four outcomes plainly — evidence, a cut, a decision, an `assumed:` tag — says a wrong finding is rebutted in `## Decisions` with a `path:line` citation, states the real stop rule (no lap while the claim check and confirming review find nothing, the budget is spent, or the text is unchanged), and says what happens to a question it parks. A pass already on record is named as a pass; the command description and `/pb:help spec-harden` were reworded the same way.

- **`/pb:spec-review` runs the pre-build review without the build.** The pass was reachable only from `startBuild`, so a plan you wanted judged before committing to it had to be approved — and usually started — first. `/pb:spec-review [name]` runs that same fresh, read-only pass and records that same `specHash`-bound verdict, then stops: no approval, no task, no checkpoint, and the reuse was already keyed on the spec text rather than the door, so the `/pb:build` that follows starts at T1 without a second review. Only the wording differs between the doors (`reviewDoor(name, "build" | "standalone")`: what `Next:` offers, what a P0 costs, whether a stored pass is re-shown), so a P0 found on demand holds the later build exactly as one found before T1 does. Two things come with a longer gap between pass and build, and both are said rather than gated: the event stamps the `head` the reviewer read the repo in, and a re-posted verdict names it when HEAD has moved (a pass covers the spec's bytes; the code its citations point at can move — it cannot void the pass, since uncommitted drift moves no HEAD); and at this door a stored pass is *shown* with its findings, because here the verdict is the answer rather than a step into T1. Ask about a spec whose build is running and the plan review comes labelled as advice — it re-gates nothing, because `startBuild` still re-reads the text and compares hashes before anything is approved.

- **The review's isolation holds against tools Pi activates late.** A review session's tool set was enforced only by `setActiveTools` at `session_start` plus an `edit`/`write` block in the `tool_call` guard — but Pi activates a tool on registration, and the built-in MCP extension registers its tools when a server connects, after that: a "read-only" reviewer could end up holding an MCP tool (or, with a codemode-exposed server, codemode itself). The guard now blocks every tool outside `REVIEW_SESSION_TOOLS` in a review session, whichever way Pi activated it. Fresh runs are hermetic too: `--no-extensions` never stopped the built-in MCP extension from spawning the user's servers (and from Pi 1.0.4 `--tools` keeps MCP tools), so the runner passes `--no-mcp`, gated on Pi's exported `VERSION` so an older install still starts.
- **The Pi floor is `^1.5.0`.** The releases since 1.0.0 fix a provider-cache break twice per `triggerTurn` run (every handout, steer, nudge and checkpoint message), silent print-mode cut-offs (a reviewer report truncated at the output limit used to exit 0), tools dropped on resume, compaction summaries dying on reasoning-model output caps, and tool-argument validation errors the model cannot act on. pb's schemas are unchanged TypeBox, now imported from `typebox` — the same package Pi 1.5 hands its extensions — via the new `schema.ts`, whose `StringEnum` replicates Pi's own; `@earendil-works/pi-ai` is no longer imported at all, so its peer is gone (`pi-coding-agent` and `pi-tui` stay, raised to `^1.5.0`, lockfile regenerated to match). `typebox` is a `"*"` peer, not a dependency: Pi supplies it to extensions, and a package that installs its own copy is refused at startup with `[Extension issues]` and can load a second TypeBox module beside Pi's — it stays a devDependency so `typecheck` and the tests, which run outside Pi, can still resolve it.
- **A resume approves a changed contract only after showing it.** `/pb:build` re-approving a paused build's revision was justified by "a contract edited while paused is the human's revision" — an assumption, not a fact: the model gets turns while paused too. The resume now shows every changed block the contract binds (`contractDiff`: approved copy vs the live spec, Design and Decisions left out — those are the build's) and asks; declining leaves the build paused. Without a UI it proceeds and says so, as before. And the first approval now covers the text it approves: `startBuild` re-reads the spec and compares `specHash` against the reviewed text right before `approveSpec`, so an edit made while the placement dialog was open starts a new review instead of riding in on the old one.
- **A review's handover cannot leak.** `reviewNext` set the carry and then opened the reviewer session without the cancel/throw cleanup its siblings in `flow.ts` and `plan.ts` have: a cancelled or failed `newSession` left `carry.json` behind, and the next new session from the home session was silently recorded as a review session — read-only tools, and `/pb:review done` does not lift them. `clearCarry` on both paths, and a test like the build and plan ones.
- **An incomplete review stops selling `/pb:fix`.** The result numbered its findings and offered `/pb:fix 1 …`, but the findings are recorded only when the run is complete (the adversarial pass included): on a first review the numbers resolved to nothing, and on a follow-up they resolved to the previous review's list — `/pb:fix 1` fixed a different finding than the one displayed. When the result is incomplete, the next line says to fix by hand and re-run `/pb:review`, naming why `/pb:fix` cannot see these findings yet.
- **A bare `&` is suspicious.** `suspiciousCommand`'s `&` check required whitespace on both sides, so `Test: npm test&touch /tmp/x` chained shells and the pre-approval dry-run executed it in the working copy before anyone approved the spec. Any `&` chains (`&&` and `2>&1` were already caught); the flag is the whole reason the dry-run declines.
- **`/pb:compact` resets to a spec that is already current.** The "did the model write the plan" check looked for a pb write after the request — a spec with nothing left to change fails it, and every retry stamped a later `since`, so the command could never succeed and the conversation overflowed into Pi's summarizing call. A manual request now counts a parsing planned spec as written; the automatic ask keeps its strict check (a model that ignored the write instruction should not be rewarded with a reset to a stale spec).
- **`/pb:undo` counts what it restored.** The result printed the diff count taken before the confirm dialog; a file the drift guard deliberately left alone (saved while the dialog was open) was counted as restored anyway. The result now counts `restore`'s own list and names the files it left alone.
- **`/pb:archive` keeps its guard state when it fails.** `dropSessions` ran before the rename, so a failed archive left the live spec without its review runs and the fail-closed review-session records that keep its reviewers read-only. The move comes first, the GC after.
- **Smaller truths.** The planning write guard resolves both sides through `realpath` (a target spelled `/private/tmp/...` into a `/tmp` project read as "outside" and slipped the block; relative paths are covered by the raw pairing); an explicit build consumes the session's `pendingBuild` record, which otherwise silenced the stopped-agent pause for its TTL; the dead `Not:`/`Evidence:` finding machinery is gone — no producer ever wrote those fields, `storedNot` was never called, and the fix seed no longer warns about a "Not: line" that cannot exist; and the guide now says what the code does (an unanswered question stays open and decides nothing, open questions keep a spec `Status: planning`, task handouts name the spec while hooks travel in the reset summaries, the spec example carries its `Status:` line, the suspicious-command list matches the check), and the `/pb:status` and `/pb:stats` descriptions say `pb.report/2`.
- **The extension is split by role.** `index.ts` (4,467 lines — ten tools, sixteen commands, five hooks, and every phase in one closure) is now a 66-line composition root over thirteen modules: `kit.ts` (the shared machinery and the trust boundaries), `flow.ts` (the spec tools, the spec review, the build machinery, `/pb:build`, `/pb:spec`), `review-flow.ts` (`/pb:review`), `hooks.ts` (pi's hooks), `plan.ts`, `fix.ts`, `ask.ts`, `fresh-tools.ts`, `undo.ts`, `archive.ts`, `map-flow.ts`, `misc.ts`. No behaviour moved: every declaration is the same code in a new file, the suite drives it end to end, and the shared mutable `let`s (`checking`, `boundary`, `undoSummary`) became one `runtime` object because ES module imports cannot be reassigned from outside. The point is the trust boundaries: `hooks.ts`'s write guard, `flow.ts`'s approval gate and `kit.ts`'s `approveSpec`/`driftStop` are now readable one module at a time.
- **Repeated checkpoints of an unchanged tree add nothing.** `snapshot()` returns the ref tip when the written tree equals it: no commit object, no ref move, no `/pb:undo` row (`appendCheckpoint` compares rows and stores only what adds information — a row matching the last one in commit, conversation point and task list is dropped, while a step's identity (`id`/`task`) is part of the comparison, so another step's row is never dropped and `/pb:undo`'s freshly numbered rows are exempt). A planning turn that writes nothing, an explore call, a review pass — none of them grow `refs/pb/checkpoints` any more.
- **The ref moves by compare-and-swap.** Two pb processes snapshotting one repo interleave read-tip → commit → move-ref; a blind `update-ref` let the later writer rewind the tip past the earlier commit, orphaning any stored row that named it (and with it that task's `/pb:undo`). `snapshot()` now moves the ref only when it still names the tip it committed against (`update-ref <ref> <new> <old>`), and a lost race re-parents against the fresh tip; a storm of six concurrent snapshot processes leaves every commit they recorded reachable.
- **`/pb:undo` row ids are numbered from the list that is saved.** They were counted over the pre-undo list while the undo drops the rows from the target on, so an undo–rebuild–revert cycle could re-issue an id that a surviving row still held — and `/pb:undo uN` resolves to the first match, restoring an older state than the tip printed. Ids now come from the highest `u` number in the kept rows.
- **A shut-down session leaves nothing behind in memory.** `session_shutdown` prunes every session-keyed registry (`specStarted`, `specWriting`, `compactStalls`, `checkpointing`, `checkpointQuiet`, `baselineSessions`, `planningWriteNotes`) for that session: keys are session file paths, so a replaced session's entries used to live as long as the pi process. Memory only, on purpose — the on-disk review state outlives its session because the read-only guard reads it.
- **The lockfile can no longer drift from the pinned peers.** `peerDependencies` is `^1.0.0` for all three `@earendil-works` packages instead of `*` (a breaking Pi change broke pb silently), and a test pins `package-lock.json`'s peer ranges against `package.json`, which `npm ci` refuses to disagree with.
- **`/pb:stats` tells the honesty story.** A `Precision` line per spec: findings the reviewers reported (the post-verification tally plus what the verifier dismissed), how many the second look dismissed — their share of the reported — and how many distinct findings the fix laps fixed. Computed from events that already exist; no new instrumentation. The card's `Session` line no longer counts questions, and the report's dead `context.asks` count is gone with it — nothing ever wrote an ask event — announced as the new schema id `pb.report/2`.
- **A per-task test proof that fails honestly.** `node scripts/verify-test.mjs "<exact test name>" …` runs the suite with the names as a pattern and reads the TAP report: it exits 0 only when every name ran and passed (`# SKIP` and `# TODO` are not proofs — a bodyless todo prints `ok` with `# fail 0`), the run reports `# fail 0`, and the runner itself finished cleanly (killed, timed out at ten minutes, or truncated output proves nothing even when the TAP looks green). `node --test --test-name-pattern=<zero-match>` exits 0; this cannot pass by matching nothing.
- **A fresh reviewer can report.** Pi's `--tools` replaces the whole tool selection, extension tools included, so a role that does not name its reporting tool never has it: the pre-T1 spec reviewer ran with `read,grep,find,ls` while its prompt told it to call `report_findings`, so a real review always ended "the reviewer returned no findings" and `/pb:build` could never start — the same omission the new background adversarial pass inherited. Both name it now (as the verifier and cartographer always did), and `test/mock-pi.mjs` honours `--tools` the way Pi does, so a future role that forgets its tool fails the suite instead of shipping a review that can only fail closed. A review that reports nothing now also shows what the reviewer wrote instead, and names `specReviewer.model` as the way to point the pass at a model that does report. Each reviewer prompt now puts the report call *ahead* of the reply ("pb reads the call, never your prose"), so a pass that explores for ten minutes records its findings before it starts writing.
- **The adversarial pass runs in the background.** It is a fresh `runFresh` process on the same frozen brief the reviewer read, not a second session you watch: no skip dialog (a pass that is due just runs), its session is saved and named in the result, and its tokens are recorded as `review-usage` so `/pb:stats` still counts what the review cost. A pass that crashes is named in the result ("its findings are missing, so this result is incomplete") and does not count as done, so the verdict is never recorded as complete without it. The reviewer itself stays a session you watch: it is the one pass whose reasoning you may want to interrupt and question.
- **A fix lap reports numbers, not titles.** `pb_fix_done` takes `fixed` and `skipped` as the numbers the brief shows (`fixed: [1, 3]`), refused unless each is one of this lap's findings; the event still records the titles. The `claimedFindings` matcher and its whole-line/fragment matching, and the "named none of the findings" stop it could cause, are gone: a number cannot fail to attach by its wording.
- **What the build left unchecked reaches the reviewer.** Each task's `open` report, which nothing else carries, is rendered in the review brief as "What the build says it left unchecked" and labelled as a claim to verify, not evidence, beside the new-tests-never-failing list.
- **The reset has no undo, and no stored entry to undo to.** `/pb:compact` in planning still writes the spec and resets the conversation to it, on demand or at `checkpointAt`; the `undo` half is gone, and with it the `checkpointFrom` entry each planning session carried. The messages before a reset are unchanged on the branch (`/tree` still reaches them), and the spec is what the reset leaves behind. A planning progress record no longer carries the write-only `compacted` flag either: nothing read it.
- **A build never stops to ask.** `pb_ask` now refuses inside a build instead of opening a dialog: an ambiguity is the sensible reading, recorded with `pb_record_decision (assumption: true)` and checked by the reviewer. `pb_task_done blocked` means one thing — the Goal or a Contract cannot be built as written — and pauses the build for a revised spec and a new approval (`/pb:build` re-approves and resumes; the new tip `build.contract` says so). The pre-T1 "validate the spec and stop" instruction is gone with it, so nothing in the build dialogue can idle a headless run; a planning or spec-writing question that goes unanswered stays open instead of becoming a reading.
- **The reviewer cannot change what it judges.** A review pass has read/grep/find/ls and the reporting tool, no shell: the code review, the spec review and the verifier alike. The change reaches them as one frozen diff (base commit to the tree the review started on, untracked files included, capped), captured right after the review's start snapshot, so a check or a later edit cannot alter it. The "anything its commands change is listed, not reverted" caveat is gone: there is nothing for a command to change.
- **Prompts carry paths, never documents.** No build prompt pastes the spec any more: every task handout, check retry, coherence pass, reset summary and fix lap names the spec file and the sections that bind the step (`specReference`, one line), and the model reads the source. A copy could only be shortened, stale, or too big for the model reading it — and the fixed-order shortening could cut a Contract down to a line — so the binding budgets, the shortening order and the "Shortened in this copy" notice are gone. The one document a prompt still carries is the review diff, because a reviewer has no shell to produce it; the reviewer's brief names the spec and keeps the diff at the one fixed cap. The finished tasks' caveats, rejections and open items stay inline, uncapped: they exist nowhere else.
- **The red check, not a claim.** A task whose spec asks for new tests still has to have its `Test:` command seen failing before the change — that is the one cheap, objective signal that the tests check the missing behaviour. The proof is now a single field: the command that failed. A repeat run replaces it (only the latest failed run counts), a passing run clears it, and rewriting the command drops it. The stored claim and the capped failure head are gone: the harness cannot judge whether a failure is the right one, so it no longer pretends to. A command an earlier finished task already proved cannot fail again; that exemption is derived from the task list at call time (`earlierProof`), never stored, and the disclosure reaches the reviewer. A task whose tests only ever pass cannot finish: `pb_task_done` sends it back, and a command that genuinely cannot fail is a `blocked` stop the human sees at once. `/pb:stats` keeps `proven · sent back · no run could prove`, the last derived the same way.
- **Planning writes are named while they happen.** A turn that changes a project file during planning is posted as soon as it settles ("Changed while planning", one note per change set), instead of surfacing only at `/pb:plan off` or the build start. The end-of-planning keep-or-restore review is unchanged.
- **Requirements are the spec's contracts, versioned with it.** The living requirement base, its `## Requirements: <capability>` delta grammar (`ADDED`/`MODIFIED`/`REMOVED`, `Overview:`, `Invariant:`, scenarios and `R` ids), the merge preflight and its rollback are gone (`extensions/pb/requirements.ts` is deleted). A capability's durable rules now live in the spec that changed them, are approved and reviewed with it, and are versioned by git and the archived spec. There is no second copy to drift: a later feature states the rule it changes in its own spec. `specs/` and the `## Requirement rules` handout block are gone with it.
- **One spec review, on the frozen draft.** The pre-T1 review is one independent pass: it reports findings with `report_findings`, and only a P0 (a security or authorization hole, data loss, or a contract contradiction that cannot be built as written) blocks. P1-P3 are advisory: shown to you, recorded beside the spec, and the build proceeds. A `specReviewer` mode is no longer needed, so `mode`, `maxRounds`, `/pb:build --review` and `/pb:build --force` are gone with the round, carry, delta-round, outside-lane, stable-`F`-id, advisory-cap and format-repair machinery that served them; a run that reports nothing fails closed instead of reading as a pass. Editing the spec makes the next `/pb:build` review the new text; an unchanged spec reuses its recorded verdict, re-posting a standing P0 rather than running again.
- **One acceptance form: tasks.** A spec's `## Acceptance criteria` section and the `A` ids are gone; the reviewer's checklist is each task's `- Acceptance:` lines (`T1.1`, …). A capability's rules are no longer a second checklist either (`R1.1`-style ids are gone). Per-line proof markers (`(tests: …)`, `(non-testable: …)`), the `Tn` mapping rules, `mappingNotes` and the acceptance-proof mapping gate are deleted; a task's `Test:` command is its proof, and a task with no command is judged as docs/refactor behaviour. Existing specs stay readable: an old A section and old markers are inert prose.
- **Semantic shape is the reviewer's, not a regex.** The write tools now refuse only what a parser can decide: a spec that doesn't parse, missing required sections, duplicate task ids and citations that point at no real line. Threats, measurements, evidence, reasons, Contracts and migration answers are no longer inferred from keyword lists, so an honest spec that mentions "session" or "200ms" writes cleanly; the spec reviewer and the human judge its shape there.
- **A bound names the code that owns it, and a finding names one fix.** Writer guidance says a `## Contracts` bullet that says how often something runs should name the code whose call that bound limits — a `path:line`, `new: <path>` when nothing performs it yet, or an `Assumption: … settles by …` for a cadence nothing in the project enforces — and the reviewer checks it. A backticked command measures, it does not own a cadence, and a count or a duration (`at most 200 tokens`, `200ms`) keeps its own answer: a measurement. On the review side the reviewer commits instead of hedging: one `Fix:` (the single change it would make, with its reason), a `Not:` line for any alternative it weighed and rejected, and a fork a read can settle is settled there and cited by `file:line` — never the full suite, never an either/or. That `Not:` line survives: parsed in any order (so it can no longer swallow `Fix:`), capped at 500 characters, rendered in the human post, and handed to `/pb:fix` labelled as already rejected. It reaches neither the review ledger nor the project map, so a discarded idea never becomes a future lead. The rule lives in the spec reviewer's system prompt, and the reviewer commits to it in structured findings.
- **Stale-path warnings name only real absences.** A backticked name in the project map is now read as a name only when it is shaped like a path — a slash, a leading dot, or a root file name such as `package.json` — so a code symbol like `Store.config`, `process.env` or `thread.lock` is never reported as a missing path, however the repo is built; the accepted silence is a stale name written bare (`gone.md`). A checked name resolves from the project root, under the path a heading names, as the end of a real file, or in a gitignored file of the working tree outside `node_modules/` (so `pb/config.json` finds `.pi/pb/config.json`), and never above the project root — the same containment a spec's `path:line` citation now gets, so a spec cannot fish for a file outside the repo through the refusal text. A token is a name only when its last segment carries a letter or a digit, so `.` and `..` are prose. A genuinely gone path is still reported, still sent back to the cartographer once, and still named in the approval dialog. All the missed names are asked of one `git ls-files` together, and a git that refuses, times out, or is handed more than 200 of them leaves every one flagged exactly as today.
- **A section can't be emptied by an empty replace.** `pb_update_spec` refuses a replace whose body is blank or whitespace: the heading would stand over nothing, and an empty section silently deletes what later readers and the reviewer rely on. The format's own spelling for a section with nothing to say, `none — <why>`, stays legal, and `append` is untouched.
- **Contract values show their arithmetic.** Contracts must now give every formula or derived figure — a size, limit, count, threshold, window — its computed value for each case Acceptance pins, inputs and result together (a tenth of a 128k window = 12800), because a number the reader must recompute by hand is the one that survives a review wrong. It is guidance for the writer in the spec format, not a linter: prose arithmetic cannot be parsed reliably, and a false "lint passed" is worse than none.
- **A spec-review finding reads like a work item.** Its title is one sentence you can act on — what goes wrong, for whom, and where — and the supporting trace sits on its own `Evidence:` line, separate from `Fix:`. The chat result puts earlier findings (with their resolution status and evidence) under their own heading and new blockers under another, so a fresh `F12` cannot be mistaken for a re-listing; unresolved earlier blockers are not repeated. The recorded review and linked session keep the full text.
- **A handout names the spec, and the model reads it.** The compact copy is gone; the handout, retry and coherence pass name the spec path and the binding sections, so a long spec is never truncated and a spec edited mid-build is never quoted from a stale copy. The cost is one `read` per task, and the check plus the review catch a model that skips it.- **What binds a step is one list, and nothing caps it.** The reviewer's and the builder's idea of "what binds" comes from the same exported list (Goal, Out of scope, Decisions, Design, Contracts, Migration and rollback, Threats and abuse, with `Threats` as the short form), and `specReference` names that whole list in every build prompt, so the two can no longer disagree about Out of scope. The per-section caps and the window-share budgets are deleted with the copies they sized.- **A review lead cannot break the project map.** Finding text is neutralised both where it is stored and where it is read: control characters and HTML comment markers go, every word stays, and a finding whose title is nothing but markup keeps a `(untitled finding)` placeholder instead of vanishing from the ledger. Every map write is guaranteed marker-, control-character- and tab-free, and the map's markers are read a line at a time, with fences counted from the top of the file — a marker shown in a properly fenced example stays documentation wherever the example sits, above your map as well as inside it, and a ``` you never closed above your map no longer hides its markers — where an unclosed fence still leaves pb a marker outside it, pb keeps trusting the file's fences and reports an unterminated section rather than guess at one. Where the markers cannot be resolved (an end missing, or a marker standing twice) pb writes nothing at all, names the file and the marker before any cartographer is run, and leaves your text after the stray marker and the previous-map backup exactly as they were.
- **One reset trigger.** A build session resets at the next task boundary once it passes `checkpointAt`, or before Pi's own compaction reserve (`window - PI_RESERVE_TOKENS`), whichever comes first. Planning checkpoints still reserve for the spec they write (`2 × its tokens`). The build-specific working reserve, the spec-view budget and the "sized from the view it writes" rule are gone with the copy they sized.- **A fix lap's report is matched to the finding, not to its echo.** `/pb:fix` now recognises a lap that reports the whole line it was shown (`1. [P1] src/a.ts:12 — title`), a piece of it, or that with prose around it, so a fixed finding counts as done on the first lap instead of being re-fixed until the lap cap runs out and the summary names it as fixed three times and still open. A report pb cannot attach to any finding stops the loop at once and says so — resending an unanswerable seed buys nothing — and every outcome now ends by pointing at `/pb:review`: what a lap reports is its own claim, not a check.
- **Review findings feed the project map.** Completed reviews append a capped P0–P2 `review-findings` event (place, line, fix, outside flag); a dedupe/count ledger survives the review files and the archive. `/pb:archive` hands the ledger to the cartographer as a separate "leads, not evidence" section, and a review finding alone makes the map news. The cartographer must verify every lead against the current code and leave out what no longer holds.
- **Narrow tasks, literal edits.** A build task now says to make only its own coherent change and leave the full suite to the harness after the last task; if the task has grown into several changes, it finishes the smallest part and reports the rest as open. Spec writing and the pre-T1 review split a task that bundles several independent changes with a full verification, and a task that names a full-suite run gets an advisory. Structured files (`pom.xml`, JSON, YAML) are edited by exact literal replacement or line-based edits, never by a backtracking regex — a nested-quantifier pattern such as `(?:(?!-->).*?)*` can run for minutes on a real file.
- **Every real issue is reported with its own class, and a newly reachable one keeps its priority.** A pre-existing problem is an `outside` finding instead of prose: it keeps its file, line, priority and fix, is capped at P2 and advisory, and lands under its own "Outside the change" section — so it survives compaction, reaches `/pb:fix`, and stays visible in `pb.report/1`. The rule is shared by the reviewer and the adversarial pass, and it has one exception: a problem the change makes newly reachable or materially worse is in the change and keeps its priority, so the class cannot wave a serious problem through. A reviewer's closing prose is only for what is not a finding. The verifier judges an outside finding on whether the problem is real, never on whether this change caused it.- **Spec contracts carry their evidence.** Every observable value in Contracts — a status, error, header, ordering, event name or stored value — must cite the code path or test that pins it today, or be written as an Assumption. The writer is told to open that code before writing the value, never infer a status or an order from the design, and the spec review opens each citation and treats a value that is uncited or contradicted by its citation as a finding (P1 when the build would implement a wrong contract or a test that fails against correct code).
- **Tests for overlapping classifications.** The reviewer, the adversarial pass and the spec review now exercise an input that matches more than one class (a kind, role, mode, type, state, host, tenant) and check which class wins at each decision — routing, lookup, authorization, default. Two classifiers that disagree on one input are a finding when the disagreement reaches a decision. A test named as proof must reach the branch the change relies on; a sibling branch that produces the same failure proves only itself.

The spec needs only Goal, Decisions and Tasks (Out of scope, Context, Acceptance criteria are optional), with decisions stated as they stand now, without dates or history. Comments explain the code as it is, never its history (no dates, "decided", previous values, task ids, revisit notes), with a one-line reminder in every task. No more "best solution even if more work", in the prompts or the default standards. Test output sent back to the agent: 30 key lines and a 40-line tail, 4,000 characters by default
- **No more gap check at the start of a build**: it cost too much context and stopped the build over points the model could resolve itself. The build now starts with T1 and treats the spec as settled. Where the spec is ambiguous, contradicts itself or doesn't match the code, the builder takes the sensible reading, records it as an assumption in the spec's Decisions (`pb_record_decision` with `assumption: true`) and carries on; it asks only about choices that change behaviour, an API or data. The build summary lists the assumptions and the reviewer checks them. `pb_spec_gaps` is removed
- `/pb:spec` runs a consistency pass before writing (examples against rules, acceptance against tasks, "unchanged" against "extended", every path and name against the code), fixes what it finds in the spec, and tells you; specs state each fact once
- **Stats**: the explorer's calls, compactions, prunes, reminders and questions; after a new plan in a build's session, its turns no longer count for the finished spec
- A progress line above the editor shows the build's tasks
- The build ignores `.pi/` except its spec
- The build session runs on the model and thinking level of the session you ran `/pb:build` from; a new Pi session would otherwise start from your settings' defaults (e.g. without thinking)
- Removed leftovers of wf: unused JSON-block parsing, transcript and session options in the runner, the diff summary and merge flags in the checkpoints

## 1.0.0

pb replaces wf: a simpler flow built around a self-contained spec, a fresh build session and harness-run checks. Renamed from pi-ledger-workflow to **pi-plan-build**.

- `/pb:plan <what you want, in your own words>`: plan together. Pi investigates freely (bash, the build and tests, curl, one-off scripts or programs in a temp directory) while edits to the project's files are blocked for that session (a `tool_call` guard that survives restarts); `/pb:plan off` lifts it
- `/pb:spec [which]`: Pi writes one spec per feature through `pb_write_spec`, which validates the format (header with depends-on, verification and new-tests lines; Goal, Out of scope, Decisions with rejected alternatives, Context, Acceptance criteria, Tasks) and rejects what doesn't parse
- `/pb:build [name]`: a new session seeded only with the spec. The agent first checks the spec against the code (`pb_spec_gaps`); gaps pause the build. The harness then hands out the tasks one by one; the agent finishes each with `pb_task_done`, and the harness runs its check (`tests`: the task's test command and the full suite at the end; `build`: compile/typecheck only; `none`). Failures go back to the agent until `maxAttempts`, then the build pauses; `/pb:build [guidance]` resumes. Decisions made during the build are written into the spec (`pb_record_decision`). `New tests: no` builds without adding tests
- `/pb:review [focus]`: a fresh check, then one fresh reviewer with the spec, the diff and the check result, but not the build conversation; findings land in the session, verdict pass/changes needed
- `/pb:undo`: per-task snapshots in git's object store (never touching your branch or index), reversible; deleting, cutting or skipping existing tests fails a task's check
- An unfinished build whose session is gone (e.g. after a crash) can be restarted from any session with `/pb:build`; finished tasks stay done
- Planning and build sessions are named ("plan: …", "build: <spec>") so `/resume` finds them, and their first message shows `pi --session <id>`; `/pb:status` shows each build's session
- Spec names complete as you type after `/pb:build`, `/pb:review`, `/pb:stats` and `/pb:archive`
- `/pb:status`, `/pb:stats [all]` (first-try rate, checks, pauses, review, the build session's tokens, cache share, peak context, cost, time), `/pb:archive` (to the git-ignored `.pi/pb-archive/`), `/pb:help [topic]` and a What-now block after every step
- The quality bar (best practice, clean, secure, current APIs, no quick fixes) and the comment rules carry over into planning, building and review
- Removed with wf: the fresh manager/worker loop, the ledger files, the tester and parked spec tests, merging, escalation, `/wf:models`
- Requires Node ≥ 22.19 (Pi's minimum); TypeScript 7
