## Engineering standards

- Quality: the best current practice for this stack: clean, maintainable, secure; a proper fix, never a workaround. Names say what the thing is or does: no abbreviations beyond domain terms, no generic verbs like handleData or processInfo. Use modern idioms and the latest stable language and platform features, even where the surrounding code doesn't. When outdated code stands in the way, refactor it to current practice, planned as a task of its own.
- Dependencies: current, non-deprecated APIs and versions only. Upgrading dependencies is a change of its own, not part of a feature.
- Comments: concise, and only where they add what the code can't say (why, intent, constraints). They describe the code as it is, never its history: no dates, "decided", previous values or task ids; decisions stay in the spec.
- Tests: test behaviour, written to current best practice for this stack even where existing tests aren't; new test tooling is proposed as a task of its own. Never weaken an existing test. A test proves a fix only if it fails without it.
- Security: assume every entry point (API, UI action, command, message, file, webhook) will be abused by someone who controls its input, holds a stolen or another user's session, and replays or automates requests. Each operation checks who the caller is, what they may act on, and what they have proven; logic reused from another flow keeps that flow's preconditions (a write that is safe behind an emailed token is not safe behind a session alone). Security-relevant changes get tests for their abuse cases, written from the attacker's side. When something gains trust or changes hands (verified, accepted, promoted, transferred), whatever was set up before the proof by someone who hadn't proven anything (credentials, sessions, linked identities, settings) is discarded or re-proven, not inherited.
- One source of truth: a rule or canonical form that already exists (in the database: normalization, uniqueness, constraints; or in a shared helper) is used, never re-implemented. Compare against the database's own form in SQL; a second copy of a rule drifts, and the gap between copies is a bypass.
- Robustness: at a boundary, assume input is hostile or broken (sizes, ranges, encodings, duplicates, order, concurrent calls); business rules can't be bypassed by quantity, repetition, reordering or racing; every request's work is bounded; a failure halfway leaves consistent state. Values that will be stored, compared or sent (addresses, identifiers, URLs) are validated strictly: no control characters or whitespace, and nothing that Unicode normalization would change. Inside the boundary, rely on invariants (types, constraints, transactions), not repeated checks.
- Consistency and concurrency come from the database: one request is one transaction on one connection. Use constraints, single atomic statements (`ON CONFLICT`, `UPDATE … RETURNING`) or row locks; not check-then-write in application code, retries, or extra transactions (`REQUIRES_NEW`), unless the reason is stated where it's used. State transitions are guarded by the current state (`WHERE status = …`), so repeating one is a no-op and a fact recorded once (a verification or creation time) is never overwritten.
- Before calling a change done, re-read the diff as an attacker and as a race: a stolen session, a replayed or concurrent request, a look-alike or malformed input, an attacker who acted before the victim, a failure halfway. Search for existing copies of any rule you touched.

## Project map

### Layout
- `index.ts` is the composition root; `kit.ts` holds the shared machinery and the trust boundaries (the approval gate, `driftStop`, the spec guards). Roles live in their own files: `plan.ts` (`/pb:plan` & friends), `flow.ts` (the spec tools, the spec review and its repair laps, the build machinery, `/pb:build`, `/pb:spec`, `/pb:spec-review`, `/pb:spec-fix`, `/pb:spec-harden`), `review-flow.ts` (`/pb:review`, `pb_report_findings`), `hooks.ts` (pi's hooks: compaction, checkpoints, planning protections, per-session cleanup), `fix.ts`, `phase.ts` (the build's lifecycle: the phase transition table and `nextStep`, pure), `declarations.ts` (names a diff declares, for the handoff), `ask.ts` (`pb_ask`), `fresh-tools.ts` (`pb_explore`, `pb_try`), `archive.ts`, `undo.ts`, `map-flow.ts`, `misc.ts` (stats, standards, status, help), `next.ts` (where a spec stands and its next step, pure), `command-guard.ts` (the shell rules, pure) and `fresh-guard.ts` (those rules inside the pb_explore/pb_try processes).

### Security invariants
- A repair lap cannot promote itself: it writes only through `pb_write_spec` (format gates, spec guards),
  its probe (`pb_try`) is read-only, `pb_spec_fix_done` accepts a report only from the session named in
  `Progress.fix` and only for the finding numbers that lap was shown, and the claim check records
  `spec-check`, never `spec-review` — so no repair run can satisfy the build's review gate. (security)
- `pb_explore` and `pb_try` run guarded: their processes start with `--no-extensions`, so pb's own shell hook is not there; `fresh-guard.ts` is loaded into both with `-e`, its settings handed over in `PI_PB_GUARD` (`guardSettings`, kit.ts), and it fails closed (no shell) without them. The rules live once in `command-guard.ts`, shared with hooks.ts: the explorer's shell is an **allowlist** of read-only inspection commands (no redirects, chaining, substitution or background), a probe's refuses commands that write to a system outside the machine (`remoteWriteRefusal`: a heuristic), and both shells run with credentials removed (`scrubPrefix`: database, cloud, cluster, agent and token variables unset, the common tools' credential files pointed at /dev/null; Pi's own process keeps its model keys). The env scrub, not the pattern list, is what keeps a probe off production: never weaken it to make a probe work; it has no configuration on purpose. (security)
- Shell limits come from `commandCap` everywhere: the project's own long commands (`longCommands`, kit.ts: suite, compile, lint, extra checks, every live spec's Test:) get `longCommandSec` (the larger of commandTimeoutSec and verifyTimeoutSec), ordinary ones commandTimeoutSec, and inside a run no command gets more than the run has left. A Pi bash timeout gets a note naming the limit that fired and how to raise it (hooks.ts and fresh-guard.ts). The explorer run itself has `explorer.idleSec` (no progress: no tool call or finished message, `runFresh`'s `idleMs`) and `explorer.timeoutSec`; a probe has `probeTimeoutSec`.
- A spec may cite a sibling repository (`../<repo>/<path>:<line>`, a change spanning a backend and its frontend), and only through `resolveSiblingFile` (`extensions/pb/map.ts`): the real path (links followed) must stay inside the folder that holds the project and outside the project, with no dot-named part, and never when that folder is a filesystem root. Anything else is "not in the project" and the error says nothing about the file it names. `specPathErrors` and `unresolvedAnchors` share it. (security)
- A spec name never becomes a path directly: `specDir` (`extensions/pb/store.ts`) is the only spec-name→path point; anything that is not `KEBAB_NAME` (`extensions/pb/names.ts`) or the name of an existing spec dir throws before a path is built. (security)
- A build tool may only record into the build its own session owns, and only the current step: `specForSession` (realpath-compares the session file) → `buildOfSession` throws unless `phase === "building"`, and `pb_task_done`/`pb_tests_red` refuse `params.task !== p.current` (`extensions/pb/flow.ts`). The tool is never the place to relax this. (security)
- Review sessions are read-only by the `tool_call` guard (`extensions/pb/hooks.ts`), which blocks every tool outside `REVIEW_SESSION_TOOLS` for any session holding a `reviewSession` record — not just `edit`/`write`, because a tool Pi activates after `session_start` (a late-connecting MCP server's, say) must not reach a reviewer; the pass re-marks the new session fail-closed inside `newSession`'s `withSession` (`extensions/pb/review-flow.ts`), so stolen or expired handover state cannot yield a writable reviewer. `pb_report_findings` separately refuses any session without that record. (security)
- A repair lap can write only its own spec: the same `tool_call` guard blocks every tool outside `REPAIR_SESSION_TOOLS` (`extensions/pb/kit.ts`: read/grep/find/ls, `pb_try`, `pb_ask`, the spec tools and `pb_spec_fix_done`) for a session owning an open lap, and `pb_write_spec`/`pb_update_spec` separately refuse a name other than that lap's spec. (security)
- Planning mode's project protection is three-layer: the same `tool_call` hook blocks `edit`/`write` at in-project paths for sessions in `planningSessions()`; `agent_settled` (flow.ts) posts the files that differ from the planning snapshot as soon as a turn ends (`changedPaths` against a fresh snapshot); and `reviewPlanningChanges` asks keep-or-restore at the end of planning — paths outside the project are deliberately allowed (scratch). (security)
- A review cannot mutate what it judges: the code-review session's tool set is `REVIEW_SESSION_TOOLS` (read/grep/find/ls plus `pb_report_findings`, no shell), and the fresh spec reviewer, verifier and adversarial pass get the same four read tools (the pass reports with `report_findings` through `REVIEW_TOOLS`). The change reaches them as `reviewDiff` — one `gitDiff`+`untrackedText` capture taken right after the review's `before` snapshot, capped at `REVIEW_DIFF_CHARS` — so a check or a later edit cannot change it. The verifier is handed that same diff. (security)
- Model-authored text never reaches a markdown container unsanitised: `safeLine`/`safeBlock` (`extensions/pb/markdown.ts`) strip control characters before comment markers and repeat to a fixpoint; every stored ledger field goes through `ledgerField`/`cap`. Pinned by the test "review ledger: an injected marker cannot reach the project map". (security)
- `Test:` commands run through `runVerify` with `shell: true` on purpose (they are spec-approved shell); `suspiciousCommand` (`extensions/pb/kit.ts`) flags shell chaining/network in `specWarnings` and the pre-approval dry-run declines to execute those commands — never move that check out of the flag. (security)
- A passing spec review covers exactly the text it saw: `ensureSpecReviewed` (`extensions/pb/flow.ts`) reuses a `spec-review` event only while `specHash(markdown)` matches, and only a P0 blocks. Two doors reach that one pass — on the way into a build, and on demand from `/pb:spec-review` (`reviewDoor(name, "build" | "standalone")` carries only the wording; the recorded event and the reuse are shared), so a standalone pass is what the following build rides on instead of reviewing again. `/pb:spec-review --fresh` is the deliberate exception: it bypasses the reuse and pays for another pass at the same text. Neither door re-reviews a spec edited after T1 started: that is the code reviewer's. The event also stamps the `head` the pass read the repo at, and a re-posted verdict says so when HEAD has moved — information only, never a second gate (uncommitted drift moves no HEAD).
- `/pb:spec-review` records a plan-level verdict but gates nothing: only `startBuild`'s own re-read of the text (`specHash` against the reviewed bytes) precedes `approveSpec`, so a mid-build standalone pass cannot carry a build past an unreviewed or edited contract. (security)
- pb's own check outranks a review's reviewers: `/pb:review` runs `finalCheckCommands` (kit.ts; the same list the build's final step and a fix lap run) and then each finished task's `Test:` (skipping a `suspiciousCommand`), puts every result in the brief, and stores the failed commands on the run (`ReviewRun.failedChecks`); `reviewMessage` turns a PASS over any of them into UNVERIFIED naming the command. Never let a review pass over a red check.
- `/pb:build` asks at most one question about the build itself, after the spec review: the build-start screen (`startBuild`, flow.ts) lists every concern `preBuildChecks` and `openP1s` collect (an unbuilt dependency, a red baseline, the review's P1s) plus where to build when the session is full or the model switches, and offers build (here/fresh), repair first (P1s only) or stop. Keep-or-restore of files changed while planning stays its own question. A new concern is added to that list, never as a dialog of its own.
- A timed-out choice posts what pb did (`choose`, kit.ts), and while any dialog is open the footer reads "pb · waiting for your answer" (`ui_prompt_start`/`ui_prompt_end`, hooks.ts).
- `/pb:archive` asks before archiving a spec that still owes work (`owedOnArchive`, archive.ts: build unfinished, never reviewed, last verdict not pass, open P0–P2 findings) and refuses a name that isn't `KEBAB_NAME` before any path is built; headless, it archives and says what was left.
- A `/pb:fix` lap's outcome is pb's, not the lap's: `driveFix` (`extensions/pb/fix.ts`) runs `checkAfterLap` after every report — each reproducing test the lap saw fail (it must pass now), then the build's final-step checks (`finalCheckCommands`) — and a red result keeps the lap's findings open and hands the failure to the next lap. `pb_fix_done` counts a finding as fixed only with a `pb_fix_red` proof (the command pb ran and saw fail, stored by number in the `FixSession` record) or an `untested` reason. Reports are read by finding number (`fixedIds`), never by title. Each lap is a `kind: "fix"` checkpoint row (files and spec, no conversation point; `/pb:undo` sets no task back to todo for it), and fix-lap `check` events (`task: "fix"`) stay out of the build's per-task stats.
- A `/pb:fix` lap may change only its own spec's Design and Decisions: `pb_update_spec` refuses any other section, another spec and a status change for a session holding a `fixSession` record, and `pb_write_spec` refuses it outright (`extensions/pb/flow.ts`). Both sections are outside `contractText`, so a lap's edit never needs re-approval, and it keeps the spec's `writtenIn`. A contract change stays a skipped finding for a spec revision. (security)
- Handover state is single-use and scoped: `takeCarry` (`extensions/pb/store.ts`) consumes the handover file in the pb state dir, enforces a 60-minute TTL, and returns it only to the child of the recorded parent session; every cancel/throw path calls `clearCarry` (`extensions/pb/store.ts`, `extensions/pb/flow.ts`, `extensions/pb/review-flow.ts`) — a leaked carry turns the next new session from the home session into a read-only review session.
- `/pb:undo` restores files, task state and conversation but never moves the branch; the task snapshot in each checkpoint is what drops red proofs with the files. A repair lap's row also carries the spec text and phase, restored from the row because the spec is outside the snapshots, behind the same drift guard. Its result counts what `restore` actually restored plus the spec it rewrote, and names the files the drift guard left alone — never the pre-dialog diff count.
- `/pb:undo` numbers its row from the highest `u` id in the rows it keeps, never from a count over the pre-undo list: the undo drops the rows from the target on, and a count over those can re-issue an id a surviving row still holds — `/pb:undo uN` resolves to the first match, so a duplicate would restore an older state than the tip printed.

### Session-keyed state (extensions/pb/kit.ts, extensions/pb/hooks.ts)
- Every in-memory registry keyed by a session path lives in `kit.ts` (`specStarted`, `compactStalls`, `baselineSessions`, `specWriting`, `checkpointing`, `checkpointQuiet`, `planningWriteNotes`) and must be cleared in `pruneSession`; `hooks.ts`'s `session_shutdown` handler calls it after `cleanupIndexes`. A new session-keyed map not listed there leaks for the life of the pi process (keys are session file paths, so reload/new/resume orphans them). Pinned by "session shutdown prunes every session-keyed registry for that session" and "session shutdown leaves other sessions state intact".
- Prune covers memory only, on purpose: the disk-side per-session files are not swept — `reviews/<sha1>.json` must outlive its session because it is the fail-closed read-only guard above, and orphaned `baselines/*` are a separate decision.

### Spec write gates (extensions/pb/spec.ts, extensions/pb/kit.ts, extensions/pb/flow.ts)
- The write tools refuse only what the parser can decide: parse errors, required sections, unique task ids and cited `path:line` claims. Semantic shape — Threats, measurements, evidence, reasons, Contracts, migration answers, proof quality — is the reviewer's and the human's job.
- Task acceptance is the only review checklist: `acceptanceCriteria` (`spec.ts`) yields `T1.1`, `T1.2`, … from each task's `- Acceptance:` lines. A task's `Test:` command is its proof; there is no per-line proof-marker or mapping layer.
- A `replace` whose body is blank is refused in `pb_update_spec`: the heading would stand over nothing and silently empty what later readers and the reviewer rely on.
- The writer-facing format is `SPEC_FORMAT` (`extensions/pb/prompts.ts`); its guidance is advice the reviewer checks, not a rule a write gate enforces.
- Evidence has one rule, `EVIDENCE_RULE` (prompts.ts, built on `LOAD_BEARING`): the writer's format, `SPEC_REVIEWER_SYSTEM`, `SPEC_CLAIM_CHECK_SYSTEM` and `SPEC_FIX_RULES` all embed it word for word (pinned by "evidence: the writer, the spec reviewer, the claim check and a repair lap judge claims by one rule"). Only load-bearing claims need evidence; a value the change itself defines is proven by the Acceptance line that pins it, a claim about existing code or a service never is (a test written from the same belief passes anyway). Never restate the rule in a section or role: change it there.
- What a spec must survive is one list, `SPEC_CHECKS` (prompts.ts): the writer runs it before writing (`SPEC_SELF_CHECK`, in `specPrompt` and `finishSpecPrompt`) and `SPEC_REVIEWER_SYSTEM` checks the same lines (pinned by "spec checks: the writer runs the spec reviewer's checks before writing, from one list"). A new check goes into the list, never into one side only.
- `specLosses` (`spec.ts`) names what a write removed from the previous text (sections, Acceptance lines, Decisions entries, compared word for word); both write tools add it as a note, never a refusal — a revision may drop things on purpose.
- An assumption is written one way, `assumed: <what would falsify it>` right after its claim; `specAssumptions` (`spec.ts`) is the only parser — it also reads the older Decisions lines starting "Assumption" and skips the build's own "Assumption (build, …)" entries. The approval summary and the review's scope count come from it, so a tag a repair lap adds is shown before the build like any other.

### The spec review (extensions/pb/prompts.ts, extensions/pb/flow.ts)
- One independent pass on the frozen draft: `SPEC_REVIEWER_SYSTEM` carries every reviewer rule and `specReviewBrief` only the spec text plus "only a P0 blocks". There is no round, carry, delta or outside lane machinery to keep in sync.
- `runSpecReview` records `{type:"spec-review", verdict: "pass"|"block"|"error", hash: specHash(md)}`: a run that reports no findings call is `error` and never reads as a pass. `ensureSpecReviewed` reuses a pass or block on the same hash, re-posts a standing P0, and otherwise reviews; P1–P3 are posted as advisory and do not hold the build. At the build door `weighP1s` (flow.ts) then asks, for a P1 on the text about to be approved: build anyway / repair first / stop — showing the P1s again when the pass was reused silently, skipped when that text is already approved (restart/resume), and defaulting to build with a note when nobody can answer. It is a choice, never a gate: only a P0 blocks.
- A finding carries the check it fails (`check`, one of `SPEC_CHECK_NAMES`, read off `SPEC_CHECKS`); `toFindings` maps an unknown tag to `Other`, so model text never mints a category. `/pb:stats` counts them per check (`SpecPhase.byCheck`).
- A spec edited while the review runs is not built: the pass is discarded and the human is asked to rerun `/pb:build`, which reviews the new text. The window after the pass — the placement dialog — is guarded too: `startBuild` re-reads the spec and compares `specHash` against the reviewed text right before any `approveSpec`, and refuses on a mismatch (the sub-second gap before a fresh session's approval stays uncovered on purpose).

### Spec repair laps (extensions/pb/flow.ts, extensions/pb/prompts.ts)
- A lap repairs the **plan**, in a fresh session of its own (`driveRepair`, flow.ts: `spec-fix: <spec> · lap N`, parented to the session that started the run, on that session's model through the carry) — never in the planning conversation, whose planner role, length and stale beliefs are not the lap's. It writes through the spec tools (`pb_update_spec`
  section by section; `pb_write_spec` only when most of it changes) — so the format gates and the standards
  still bind it, and `specLosses` names anything a write removed. Before reporting it runs `SPEC_CHECKS`
  over what it changed (`specFixPrompt`), so a lap that settles one claim does not write two new ones. It is not a fresh run: it has `pb_try` (read-only probes),
  `pb_ask` (you) and the ordinary spec pen. `SPEC_FIX_RULES` is its contract: point a claim at evidence,
  delete it, decide it in `Decisions`, or tag it `assumed:` — plus a written rebuttal with a `path:line`
  citation when a finding is wrong. It never invents a worklist: `recordedFindings` (flow.ts) numbers only
  the findings recorded for the exact text now on disk, and no finding is ever carried across an edit.
- `Progress.fix` (`store.ts`) is the whole authority: it names the one session allowed to report
  (`pb_spec_fix_done` refuses any other, refuses numbers its brief didn't show, and refuses a report
  that leaves one of them out), says whose turn is owed (`stage: "lap"` → the model has the ball,
  `"advance"` → pb does), and survives a restart. One lap per session, always: `openRepair` (flow.ts)
  refuses a second while another lap is live in the calling session (a dead one is dropped instead),
  so a report always closes the lap its session owns. `advanceSpecFix` (flow.ts) is the **only** step-forward,
  and `driveRepair` runs it in the starting session after each lap (pb switches back there, so every result lands
  where the human planned), for both doors; `agent_settled` only drops a lap whose plan a build took: an unreported lap stops and says so; an unchanged
  text is not re-checked or re-reviewed; parked questions are asked before anything else; a manual
  `/pb:spec-fix` lap stops at its claim check, and only the driver chains another lap. The driver runs the
  claim check **once per run** (`SpecFixState.claimCheck`, carried across laps), after the first lap and
  before any confirming review; its claims get a lap only while `laps < maxLaps − 1` when a review is still
  in budget, so claim laps never spend the lap the confirming review's findings need. Claims handed to a
  lap are not re-checked, so the digest says they were sent to a lap (`claimsTaken`), never that none are left.
- What a lap repairs by default is `repairable` (flow.ts): P0–P2, for both doors; P3 only when named. A review that
  reports nothing (or whose text changed under it) stops the run: no digest claims a verdict on text no
  review read. `fixLive` drops a lap whose session file is gone or older than
  six hours, so a killed session cannot lock a spec out of repair.
- The claim check (`spec-check` role, `SPEC_CLAIM_CHECK_SYSTEM`) is the cheap pass that makes an
  unattended repair safe: it answers only "which load-bearing claims carry no evidence and no `assumed`
  tag" — new subjects are the spec reviewer's job. It records a `spec-check` event and **never** a
  `spec-review`, so it cannot satisfy the build's review gate; a check that reports nothing is `error`
  and stops the run rather than reading as clean.
- `/pb:spec-harden`'s stop rule is facts, not silence: budgets (`specFix.maxLaps`, `specFix.maxReviews`,
  defaults 3 and 2), nothing left to repair, or a lap that changed nothing. A fresh full review never
  runs out of subjects, so "no findings" is never the condition. `/pb:spec-fix` is the manual single lap;
  the hardening driver's `driver: true` is the only difference in the lap record.

### Build, checks and undo (extensions/pb/flow.ts, extensions/pb/undo.ts, extensions/pb/checkpoint.ts, extensions/pb/store.ts, extensions/pb/verify.ts)
- Prompts carry paths, never documents: `specReference` (`prompts.ts`) names the spec file and `BINDING_SECTIONS`, and every handout, retry, coherence pass, reset summary and fix seed uses it. Nothing pastes the spec to a builder, so nothing is shortened or stale and no text budget is needed. Two briefs still carry documents on purpose: the spec-review pass gets the whole frozen draft (it judges the hashed text, and the hash reuse depends on the exact bytes), and the review diff reaches reviewer and verifier because they have no shell to produce it (`REVIEW_DIFF_CHARS`, the same frozen capture for both). The planning checkpoint's reset summary (`checkpointSummary`) pastes the specs it resets to — the summary is the reset.
- A build resets between tasks by default (`buildReset: "task"`): `turn_end` resets at the task boundary to `stateSummary`, and `doneHandoff` names each finished task's checkpoint files in the next `taskPrompt`, directing it to inspect the parts it depends on; code is evidence, not approval, and Design is the shared-shape contract. `"threshold"` keeps the `checkpointAt` trigger; `"never"` leaves compaction to Pi. The reset happens only between tasks — never mid-task or between failed attempts.
- The build is autonomous: `pb_ask` refuses inside a build (`phase === "building"`), `buildMechanics` says so, and there is no pre-T1 implementer validation. An ambiguity is a `pb_record_decision (assumption: true)`; only a Goal or a Contract that cannot be built as written stops it — `pb_task_done blocked` pauses with tip `build.contract`, and `/pb:build` re-approves the revised spec and resumes. The resume re-approval is not unconditional: when the live contract hash differs from the approved one, `contractDiff` shows every changed block and a confirm gates the `approveSpec` — the model gets turns while paused too, so "edited while paused" is proven to the human, not assumed. `startBuild` also clears the session's `pendingBuild` record: one that survives would keep `agent_settled`'s stop-pause from firing for its TTL.
- A red proof is one field, bound to the exact `Test:` command: `syncTasks` drops `TaskProgress.redCommand` when the command text changes. Test-file fingerprints, `redShared` and `preGreen` are gone. A repeat `pb_tests_red` replaces the proof (only the latest failed run counts) and a passing run clears it; a command an earlier finished task already proved cannot fail again, so `earlierProof` (`spec.ts`) derives that exemption from the task list (nothing stored) and the disclosure reaches the reviewer through `redNotes`. A task whose tests never fail is refused by `pb_task_done` and told to stop with status `blocked` — the human learns immediately, not at review.
- Checkpoints live in refs/pb/checkpoints with a **per-process** private index (`pb-index-<pid>`): never use a shared index file, parallel sessions would fight over one lock, and a lost lock means a lost checkpoint. `restore` leaves files that drifted since its `from` snapshot alone and reports `guardFailed` instead of clobbering.
- `snapshot()` returns the ref tip when the written tree equals the tip's tree: no commit is minted and the ref does not move, so a fresh snapshot of an unchanged tree is not new information (the commit message is git-only; nothing human reads it). The ref itself moves only by compare-and-swap (`update-ref <ref> <new> <old>`, empty `<old>` = must not exist): two concurrent pb processes would otherwise let the later writer rewind the tip past the earlier commit and orphan the rows that name it; a lost race re-parents against the fresh tip, eight tries, then no snapshot rather than an orphan. Pinned by the concurrent-snapshot storm test.
- `appendCheckpoint` (`store.ts`) is the only way a `/pb:undo` row is added: it compares against the **last element of the list being written** — pass a filtered/sliced list, not the stored tail — on every field except `at`, `summary`, `files`, `declarations` (all filled in after the row is written); row identity (`id`/`task`) is part of the comparison because rows are found by id downstream, so another step's row is never dropped and freshly-numbered `uN` rows are exempt. `beginTask` and `beginCohereEntry` save only when it returns true; `/pb:undo` saves its sliced list unconditionally.
- `specWarnings` warns, without rejecting, when two tasks share one `Test:` command: one run cannot show each task's own new tests failing.
- Where lint gates a build is decided once, at its start, and stored as `Progress.lintGate` (`lintGateFor`, flow.ts): a configured `"lint"` → `"task"`; an auto-detected one → `"task"` only when the planning session's baseline ran that command clean on this commit, else `"final"` with a notice, so debt already in the code never fails T1. A restart keeps the stored gate; a build without one (started before the field existed) stays per-task (`lintsEachStep`).
- With `lintGate` `"task"`, lint gates every step, not just the end: `checkAndAdvance` runs `lintCmd` after the step's own check and fails the step on it; the final step skips lint when entered straight from a passed step (`lintDone`) and re-runs it on a retry. A task records one `check` event per attempt with a `lint` field (stats count attempts from those events), so the completion's lint gate fact comes from the last task event when the final step did not run lint.
- `doneHandoff` names, per file, what each finished task declared (`Checkpoint.declarations`, from `addedDeclarations` → `declarationsIn` in `extensions/pb/declarations.ts`: per-language patterns over added diff lines, test files skipped, capped), so a task after a reset extends a helper instead of writing a near-copy. A heuristic: a miss costs a pointer, never correctness.
- Only `runVerify` decides pass/fail; `noopCommand` (an always-passing `Test:`) is warned about because it wedges the red gate.

### Requirements are the spec's contracts (extensions/pb/spec.ts, extensions/pb/flow.ts)
- There is no requirements file, delta grammar or merge: a capability's durable rules live in the spec that changed them, approved through `approveSpec`'s `contractHash` (`contractText` excludes only Design and Decisions). `/pb:archive` keeps the approved spec; git keeps earlier versions.
- A changed contract outside the build pauses it (`approvalDrift`); the only re-approval is `/pb:build`'s, and it shows the changed blocks for a confirm first (no UI: it proceeds and says so), so no second copy can drift from the spec the human read.

### Fresh sub-agent runs (extensions/pb/runner.ts, extensions/pb/review.ts)
- Explorer, trier and cartographer get `bash` and are reverted by `revertFreshRun`; the spec reviewer and dry-run keep their revert as a belt (they have no shell any more); the **code review** names paths that changed while it ran instead of reverting, because a file changed in that window is as likely the human's.
- The reviewer is the one watched session; the adversarial pass is a `runFresh` background process on the same frozen brief, named in the result, and its tokens are recorded as `review-usage` so `/pb:stats` counts what the review cost.
- The claim check is a fresh run too: `runClaimCheck` passes `maxConcurrent`, `--no-mcp` and a
  `tools:` list naming `report_findings`, like every other fresh role.
- All fresh runs funnel through `runFresh`, whose FIFO slot cap is `config.maxConcurrent` (the project's `config.json`, else the user-level pb config merged in by `Store.config` under Pi's agent dir) overridable by `PI_PB_MAX_CONCURRENT`; new roles must pass the cap through or they bypass it.
- A fresh run can carry `timeoutMs`: the clock starts once it holds a slot (queue time is not probe time), expiry kills the whole process group like an abort, and the result says `timedOut` so a caller can name the limit. `pb_try` passes `config.probeTimeoutSec` (default 900 s, `0` = no limit); a trier's `bash` has no default timeout of its own, so this is the only bound on a runaway probe.
- Pi's own `bash`/`powershell` calls have no default timeout either: `hooks.ts`'s `tool_call` guard sets `input.timeout` to `config.commandTimeoutSec` (default 1800 s; `0` = off) before Pi runs the call, keeping a shorter timeout the model asked for and clamping a longer one; the build task prompt and the `/pb:fix` seed tell the model to stop and report a timeout instead of retrying it. Pi applies no validation after a hook mutation, so the value must stay a positive finite number.
- A fresh role names its reporting tool in `tools:` (`--tools` replaces the whole selection, **extension tools included**, so an unnamed `report_findings` / `report_verdicts` / `report_map` is never declared and the run can never report). Fresh runs also pass `--no-mcp` (Pi 1.0.4+, gated on the exported `VERSION`): MCP is a built-in extension `--no-extensions` does not stop, so the user's servers would otherwise be spawned — and since 1.0.4 their tools kept by `--tools` — inside a process that is meant to see only the brief. `test/mock-pi.mjs` refuses calls to tools `--tools` does not name, because the mock otherwise cannot see this class at all. (security)

### Stats and the machine report (extensions/pb/stats.ts, extensions/pb/report.ts)
- Events are the only source: a `review` event stores `p` (the **post-verification** P0–P3 tally) and `dismissed` as a count, a `fix` event stores fixed/skipped title lists. `/pb:stats`'s `Precision` line derives from them (`reported = Σp + dismissed`, distinct fixed titles across laps) — no per-finding identity is stored anywhere, so a single finding cannot be tracked across laps without an event-schema change.
- The spec phase is measured from its events: `spec-review` and `spec-check` carry the fresh run's tokens and cost (`runUsage`, runner.ts), `spec-fix` the lap's settled items. `summarize` folds them into `Summary.spec` (reviews, blocks, findings P0–P3, claim checks and claims, laps with applied/rebutted/parked/assumed, tokens, cost, time; a lap's own tokens are in its own session and not counted), shown as the card's `Spec` line and as `stats.spec` in the report. These numbers are what a change to the evidence rules is judged by.
- `REPORT_SCHEMA` (`extensions/pb/report.ts`; its value, the schema id `"pb.report/2"` — pb.report/1 lost the dead `context.asks` count, which nothing ever wrote) is one document for `/pb:status --json`, `/pb:stats --json` and `pb-report`; `extensions/pb/report-cli.mjs` is the `pb-report` binary, declared in `package.json` `bin` rather than by the extension. A key leaves the document only with a new schema id.

### Docs that are runtime input (extensions/pb/guide.md, extensions/pb/help.ts, README.md)
- `guide.md` is parsed at runtime: ` pb:tip key ` regions are the only source of "What now" text (`tip()`, defined in help.ts, used across the phase modules), and `pb:topic` regions are `/pb:help` sections. Using `tip("x")` without the region fails the test "help: every What-now block the code uses exists in the guide".
- `BINDING_SECTIONS` (`spec.ts`) is the single list every build prompt names for the model to read (`specReference`), and the guide and README must state it in the exported order (test "binding: the guide and README list the binding sections in the exported order"). Nothing renders or shortens the sections any more: the spec file is one read away.

### Tests + build
- `npm test` → `node --test "test/*.test.mts"` (478 tests, ~65 s: the files run in parallel); `npm run typecheck` (strict, with `noUnusedLocals`/`noUnusedParameters`, tests included); `npm run check` runs both (CI matrix: Node 22/24/26). npm + `package-lock.json`.
- The end-to-end suite is split by area — `plan`, `spec`, `build`, `review`, `core` `.test.mts` — over one harness, `test/harness.mts` (the simulated Pi, `setup()`, the `SPEC()` fixtures and the scripted agents, every helper exported). A new test goes in its area's file and imports only what it uses (the typecheck refuses an unused import); a helper shared by two files belongs in the harness. `phase.test.mts` and `prompts.golden.test.mts` are unit-level.
- `node scripts/verify-test.mjs [--file <file>] "<exact test name>" ...` is the per-task proof: it exits 0 only when every name has a TAP `ok N - <name>` line and the report says `# fail 0` (a `# SKIP` is not a proof), because `node --test --test-name-pattern=<zero-match>` itself exits 0. Names are regex-escaped; without `--file` it runs the whole suite (every `test/*.test.mts`); dev-only (outside `package.json` `files`).
- `test/verify-fixture.test.mjs` is deliberately **not** run by `npm test` (its `.mjs` extension keeps it out of the `*.test.mts` glob); the prover's tests drive it through `--file`, so they never nest the real suite.
- Peer ranges must stay identical in `package.json` and `package-lock.json` or `npm ci` refuses in CI: after touching a peer, run `npm install --package-lock-only`. Pinned by "deps: the lockfile peer ranges match package.json".
- Pi's host-provided packages (`typebox`, `@earendil-works/pi-*`) are never in `dependencies` — Pi refuses such a package at startup (`[Extension issues] … Host-provided extension packages …`) and can end up with two copies of TypeBox; they are peers, `typebox` as `"*"` (the version is whichever Pi ships) and kept in `devDependencies` so typecheck and tests resolve it outside Pi. Pinned by "deps: Pi's host-provided packages are peers, never dependencies".
- The suite drives the real commands/tools against a simulated Pi; `PI_PB_PI_COMMAND` points fresh sub-processes at `test/mock-pi.mjs`, whose `MOCK_SPEC_REVIEW` modes are `block` (a P0), `block-advisory` (P0 + P2), `advisory` (P1 + P2, a pass), `minor` (a P2 alone), `polish` (a P3 alone), `tagged` (findings tagged with their check, one unknown), `mixed` (P0 + P1), `prose` (a report written as prose, no tool call) and `crash` (no report). `MOCK_SPEC_BRIEF_OUT` captures the latest brief; `MOCK_SPEC_EDIT` simulates a human editing the spec mid-review; `MOCK_ABUSE_ARGS_OUT` / `MOCK_SPEC_ARGS_OUT` capture a fresh run's argv (its `--tools` allowlist), and the mock refuses a report through a tool `--tools` does not name.
- `setup()` sets `reviewer.idleSec: 0` and an empty `specReviewer` (the review always runs); `PI_CODING_AGENT_DIR` is redirected to a temp dir so nothing touches the real user agent dir. `MOCK_VERIFIER_BRIEF_OUT` captures the verifier's brief.
- `written()` asserts an error-free `pb_write_spec`, so any new write gate must be satisfied by the shared fixtures: `SPEC()` plus the one task-list builder `tasksMarkedBy` behind `TASKS_WITH_OWN_IDS` and `TASKS_WITH_EXEMPTIONS`.

### Standards (extensions/pb/standards.ts)
- A section is composed, never a fixed text per stack: `backend(database, stackLines)` = core, the `DATABASE` part when `usesDatabase(cwd)`, the re-read, then the stack's lines last (so a shared core stays a prefix of every stack's own and `offerStandards`' "a shared section is enough" check keeps working). Vue and your own templates are written as they are. A shared section must never carry stack or database rules: a project needing either is offered its own, never the all-projects file.
- Every project manifest pb reads for detection (package.json, Cargo.toml, pom.xml, Gradle, go.mod, Python) goes through `extensions/pb/manifest.ts` (`readManifest`, `readJsonManifest`, `packageScript`): non-blocking open, regular files only, at most 1 MB — the project's files are untrusted input, and a pipe planted under a manifest's name must not hang a command. Never `readFileSync` a manifest.

### Prompt snapshots (test/prompts.golden.test.mts, test/golden/)
- Every prompt pb sends is rendered with fixed inputs and compared with `test/golden/<name>.txt`, whose first line is its word count: information for review, never a cap. A prompt change — direct or through a shared rule — fails the test until `UPDATE_GOLDEN=1 npm test` rewrites the snapshot, so the change lands as a reviewable text diff. A new prompt gets an entry in `RENDERED`; a snapshot without one fails the suite.
- Prompts are built only in `prompts.ts` (and the cartographer's in `map.ts`), never inline at a call site, so the snapshots see all of them.

### The build's lifecycle (extensions/pb/phase.ts)
- Every phase change goes through `phase.ts`: `enterStep` (a step starts or resumes: `building`, `current`, pause cleared), `pauseAt`, `finishBuild`, `markReviewed`, and `nextPhase` for a (re)start in `initBuildProgress`. `PHASE_TRANSITIONS` is the whole lifecycle — written→building; building→paused|built; paused→building; built→building|reviewed; reviewed→building; staying put is a no-op — and an impossible move throws rather than leave a record no command can continue. `restorePhase` (`/pb:undo`) is the one move outside the table: the row is the authority. Never assign `p.phase` elsewhere (the reads that migrate a legacy `"checking"` are data repair, not moves).
- What follows a passed step is `nextStep` (task → one coherence pass when `needsCohere` → final check unless the step just ran the suite and no project check remains → done); `advanceAfterCheck` only executes the answer.

### Where you are, what's next (extensions/pb/next.ts, extensions/pb/kit.ts)
- `whereNext` (one spec) and `whereHere` (this session: fix lap, review, repair lap, build, written spec, planning, else the project's one live spec) are the **only** derivation of state and next step, computed from progress, events and the text on disk, never stored. The footer (`refreshWhere`: `ctx.ui.setStatus("pb", …)` plus the terminal title), `/pb:status`, `/pb:help` with no topic, the startup greeting and the alt+n shortcut all read it; a new phase or verdict is added there, never as a hand-written next step in one place.
- `refreshAfterCommands` (index.ts, installed before any module registers) wraps every pb command so the footer refreshes when it returns — Pi has no "a command ran" event; `turn_end`, `agent_settled` and `session_start` refresh it too. The greeting fires only on `startup`: pb's own switches back from a review or fix lap arrive as `resume`.
- Argument completion: Pi replaces the whole argument text with the chosen value, so `fixCompletions`/`specFixCompletions` build the full `<spec> <n>...` (the spec is written in when it was inferred, so the command resolves the same one).

### Planning's role (extensions/pb/prompts.ts, extensions/pb/hooks.ts, extensions/pb/kit.ts)
- The planner's role, stance, whole-system walk and ledger rule are `PLANNER_ROLE`, set as the `pb_planner` system-prompt section by `hooks.ts`' `before_agent_start` on every run of a session in `planningSessions()` (with `extra.plan` appended), and removed on any other run. Never paste the stance into a first message again: a rule given once fades over a long discussion, and `checkpointSummary` (the reset) carries the spec, not the stance. The first messages (`planPrompt`, `continuePlanPrompt`, `approachPrompt`) carry only the task, the investigation steps and the reply shape.
- The planner's model and thinking floor (`config.planner`, default floor `"high"`) are applied by `applyPlanner` when planning starts (`/pb:plan`, `/pb:deps`) and handed to a continued plan's new session through the carry; what planning changed is stored in the session's planning record (`PlannerSettings`, `store.setPlannerSettings`) — on disk, so it survives a restart, and no in-memory session registry is needed. `liftPlanning` puts back only what is still as planning set it (`restorePlanner`), so a level you chose mid-planning is kept. `plannerSettings` is the pure decision.
