## Engineering standards

- Quality: the best current practice for this stack: clean, maintainable, secure; a proper fix, never a workaround. Names say what the thing is or does: no abbreviations beyond domain terms, no generic verbs like handleData or processInfo. Use modern idioms and the latest stable language and platform features, even where the surrounding code doesn't. When outdated code stands in the way, refactor it to current practice, planned as a task of its own.
- Dependencies: current, non-deprecated APIs and versions only. Upgrading dependencies is a change of its own, not part of a feature.
- Comments: concise, and only where they add what the code can't say (why, intent, constraints). They describe the code as it is, never its history: no dates, "decided", previous values or task ids; decisions stay in the spec.
- Tests: test behaviour, written to current best practice for this stack even where existing tests aren't; new test tooling is proposed as a task of its own. Never weaken an existing test. A test proves a fix only if it fails without it.
- Security: assume every entry point (API, UI action, command, message, file, webhook) will be abused by someone who controls its input, holds a stolen or another user's session, and replays or automates requests. Each operation checks who the caller is, what they may act on, and what they have proven; logic reused from another flow keeps that flow's preconditions (a write that is safe behind an emailed token is not safe behind a session alone). Security-relevant changes get tests for their abuse cases, written from the attacker's side. When something gains trust or changes hands (verified, accepted, promoted, transferred), whatever was set up before the proof by someone who hadn't proven anything (credentials, sessions, linked identities, settings) is discarded or re-proven, not inherited.
- One source of truth: a rule or canonical form that already exists (in the database: normalization, uniqueness, constraints; or in a shared helper) is used, never re-implemented. Compare against the database's own form in SQL; a second copy of a rule drifts, and the gap between copies is a bypass.
- Robustness: at a boundary, assume input is hostile or broken (sizes, ranges, encodings, duplicates, order, concurrent calls); business rules can't be bypassed by quantity, repetition, reordering or racing; every request's work is bounded; a failure halfway leaves consistent state. Values that will be stored, compared or sent (addresses, identifiers, URLs) are validated strictly: no control characters or whitespace, and nothing that Unicode normalization would change. Inside the boundary, rely on invariants (types, constraints, transactions), not repeated checks.
- Consistency and concurrency come from the database: one request is one transaction on one connection. Use constraints, single atomic statements (`ON CONFLICT`, `UPDATE … RETURNING`) or row locks; not check-then-write in application code, retries, or extra transactions (`REQUIRES_NEW`), unless the reason is stated where it's used. State transitions are guarded by the current state (`WHERE status = …`), so repeating one is a no-op and a fact recorded once (a verification or creation time) is never overwritten.
- Before calling a change done, re-read the diff as an attacker and as a race: a stolen session, a replayed or concurrent request, a look-alike or malformed input, an attacker who acted before the victim, a failure halfway. Search for existing copies of any rule you touched.

## Project map

### Security invariants
- A spec name never becomes a path directly: `specDir` (`extensions/pb/store.ts`) is the only spec-name→path point; it rejects anything that is not `KEBAB_NAME` (`extensions/pb/names.ts`) — `.`, `..`, separators throw before any path is built. (security)
- A build tool may only record into the build its own session owns, and only the current step: `specForSession` (realpath-compares the session file) → `buildOfSession` throws unless `phase === "building"`, and `pb_task_done`/`pb_tests_red` refuse `params.task !== p.current` (`extensions/pb/index.ts`). The tool is never the place to relax this. (security)
- Review sessions are read-only by the `tool_call` guard (`extensions/pb/index.ts`), which blocks `edit`/`write` for any session holding a `reviewSession` record; the guard re-marks a fresh review session fail-closed inside `newSession`'s `withSession`, so stolen or expired handover state cannot yield a writable reviewer. `pb_report_findings` separately refuses any session without that record. (security)
- Planning mode's project protection is three-layer: the same `tool_call` hook blocks `edit`/`write` at in-project paths for sessions in `planningSessions()`; `agent_settled` posts the files that differ from the planning snapshot as soon as a turn ends (`changedPaths` against a fresh snapshot); and `reviewPlanningChanges` asks keep-or-restore at the end of planning — paths outside the project are deliberately allowed (scratch). (security)
- A review cannot mutate what it judges: the code-review session's tool set is `REVIEW_SESSION_TOOLS` (read/grep/find/ls plus `pb_report_findings`, no shell), and the fresh spec reviewer and verifier get the same four read tools. The change reaches them as `reviewDiff` — one `gitDiff`+`untrackedText` capture taken right after the review's `before` snapshot, capped at `REVIEW_DIFF_CHARS` — so a check or a later edit cannot change it. The verifier is handed that same diff. (security)
- Model-authored text never reaches a markdown container unsanitised: `safeLine`/`safeBlock` (`extensions/pb/markdown.ts`) strip control characters before comment markers and repeat to a fixpoint; every stored ledger field goes through `ledgerField`/`cap`. Pinned by the test "review ledger: an injected marker cannot reach the project map". (security)
- `Test:` commands run through `runVerify` with `shell: true` on purpose (they are spec-approved shell); `suspiciousCommand` (`extensions/pb/index.ts`) flags shell chaining/network in `specWarnings` and the pre-approval dry-run declines to execute those commands — never move that check out of the flag. (security)
- A passing spec review covers exactly the text it saw: `ensureSpecReviewed` (`extensions/pb/index.ts`) reuses a `spec-review` event only while `specHash(markdown)` matches, and only a P0 blocks. The pass runs only on the way into a build, so spec edits after T1 started are never re-reviewed at plan level.
- Handover state is single-use and scoped: `takeCarry` (`extensions/pb/store.ts`) consumes the handover file in the pb state dir, enforces a 60-minute TTL, and returns it only to the child of the recorded parent session; every cancel/throw path calls `clearCarry` (`extensions/pb/store.ts`, `extensions/pb/index.ts`).
- `/pb:undo` restores files, task state and conversation but never moves the branch; the task snapshot in each checkpoint is what drops red proofs with the files.

### Spec write gates (extensions/pb/spec.ts, extensions/pb/index.ts)
- The write tools refuse only what the parser can decide: parse errors, required sections, unique task ids and cited `path:line` claims. Semantic shape — Threats, measurements, evidence, reasons, Contracts, migration answers, proof quality — is the reviewer's and the human's job.
- Task acceptance is the only review checklist: `acceptanceCriteria` (`spec.ts`) yields `T1.1`, `T1.2`, … from each task's `- Acceptance:` lines. A task's `Test:` command is its proof; there is no per-line proof-marker or mapping layer.
- A `replace` whose body is blank is refused in `pb_update_spec`: the heading would stand over nothing and silently empty what later readers and the reviewer rely on.
- The writer-facing format is `SPEC_FORMAT` (`extensions/pb/prompts.ts`); its guidance is advice the reviewer checks, not a rule a write gate enforces.

### The spec review (extensions/pb/prompts.ts, extensions/pb/index.ts)
- One independent pass on the frozen draft: `SPEC_REVIEWER_SYSTEM` carries every reviewer rule and `specReviewBrief` only the spec text plus "only a P0 blocks". There is no round, carry, delta or outside lane machinery to keep in sync.
- `runSpecReview` records `{type:"spec-review", verdict: "pass"|"block"|"error", hash: specHash(md)}`: a run that reports no findings call is `error` and never reads as a pass. `ensureSpecReviewed` reuses a pass or block on the same hash, re-posts a standing P0, and otherwise reviews; P1–P3 are posted as advisory and do not hold the build.
- A spec edited while the review runs is not built: the pass is discarded and the human is asked to rerun `/pb:build`, which reviews the new text.

### Build, checks and undo (extensions/pb/index.ts, extensions/pb/checkpoint.ts, extensions/pb/verify.ts)
- Prompts carry paths, never documents: `specReference` (`prompts.ts`) names the spec file and `BINDING_SECTIONS`, and every handout, retry, coherence pass, reset summary and fix seed uses it. Nothing pastes the spec, so nothing is shortened or stale and no text budget is needed. The one document a prompt still carries is the review diff, because a reviewer has no shell to produce it (`REVIEW_DIFF_CHARS` in the brief, the same frozen capture for the verifier).
- The build is autonomous: `pb_ask` refuses inside a build (`phase === "building"`), `buildMechanics` says so, and there is no pre-T1 implementer validation. An ambiguity is a `pb_record_decision (assumption: true)`; only a Goal or a Contract that cannot be built as written stops it — `pb_task_done blocked` pauses with tip `build.contract`, and `/pb:build` re-approves the revised spec and resumes.
- A red proof is one field, bound to the exact `Test:` command: `syncTasks` drops `TaskProgress.redCommand` when the command text changes. Test-file fingerprints, `redShared` and `preGreen` are gone. A repeat `pb_tests_red` replaces the proof (only the latest failed run counts) and a passing run clears it; a command an earlier finished task already proved cannot fail again, so `earlierProof` (`spec.ts`) derives that exemption from the task list (nothing stored) and the disclosure reaches the reviewer through `redNotes`. A task whose tests never fail is refused by `pb_task_done` and told to stop with status `blocked` — the human learns immediately, not at review.
- Checkpoints live in refs/pb/checkpoints with a **per-process** private index (`pb-index-<pid>`): never use a shared index file, parallel sessions would fight over one lock, and a lost lock means a lost checkpoint. `restore` leaves files that drifted since its `from` snapshot alone and reports `guardFailed` instead of clobbering.
- `specWarnings` warns, without rejecting, when two tasks share one `Test:` command: one run cannot show each task's own new tests failing.
- Only `runVerify` decides pass/fail; `noopCommand` (an always-passing `Test:`) is warned about because it wedges the red gate.

### Requirements are the spec's contracts (extensions/pb/spec.ts, extensions/pb/index.ts)
- There is no requirements file, delta grammar or merge: a capability's durable rules live in the spec that changed them, approved through `approveSpec`'s `contractHash` (`contractText` excludes only Design and Decisions). `/pb:archive` keeps the approved spec; git keeps earlier versions.
- A changed contract outside the build pauses it (`approvalDrift`); nothing else re-approves a rule, so no second copy can drift from the spec the human read.

### Fresh sub-agent runs (extensions/pb/runner.ts, extensions/pb/review.ts)
- Explorer, trier and cartographer get `bash` and are reverted by `revertFreshRun`; the spec reviewer and dry-run keep their revert as a belt (they have no shell any more); the **code review** names paths that changed while it ran instead of reverting, because a file changed in that window is as likely the human's.
- All fresh runs funnel through `runFresh`, whose FIFO slot cap is `config.maxConcurrent` (the project's `config.json`, else the user-level pb config merged in by `Store.config` under Pi's agent dir) overridable by `PI_PB_MAX_CONCURRENT`; new roles must pass the cap through or they bypass it.

### Docs that are runtime input (extensions/pb/guide.md, extensions/pb/help.ts, README.md)
- `guide.md` is parsed at runtime: ` pb:tip key ` regions are the only source of "What now" text (`tip()` in prompts.ts and index.ts) and `pb:topic` regions are `/pb:help` sections. Using `tip("x")` without the region fails the test "help: every What-now block the code uses exists in the guide".
- `BINDING_SECTIONS` (`spec.ts`) is the single list every build prompt names for the model to read (`specReference`), and the guide and README must state it in the exported order (test "binding: the guide and README list the binding sections in the exported order"). Nothing renders or shortens the sections any more: the spec file is one read away.

### Tests and commands (test/, package.json)
- `npm test` → `node --test test/pb.test.mts` (310 tests, ~150s); `npm run typecheck`; `npm run check` runs both (CI matrix: Node 22/24/26). npm + `package-lock.json`.
- The suite drives the real commands/tools against a simulated Pi; `PI_PB_PI_COMMAND` points fresh sub-processes at `test/mock-pi.mjs`, whose `MOCK_SPEC_REVIEW` modes are `block` (a P0), `block-advisory` (P0 + P2), `advisory` (P1 + P2, a pass), `mixed` (P0 + P1) and `crash` (no report). `MOCK_SPEC_BRIEF_OUT` captures the latest brief; `MOCK_SPEC_EDIT` simulates a human editing the spec mid-review.
- `setup()` sets `reviewer.idleSec: 0` and an empty `specReviewer` (the review always runs); `PI_CODING_AGENT_DIR` is redirected to a temp dir so nothing touches the real user agent dir. `MOCK_SPEC_ARGS_OUT` captures the spec reviewer's argv (its `--tools` allowlist); `MOCK_VERIFIER_BRIEF_OUT` captures the verifier's brief.
- `written()` asserts an error-free `pb_write_spec`, so any new write gate must be satisfied by the shared fixtures: `SPEC()` plus the one task-list builder `tasksMarkedBy` behind `TASKS_WITH_OWN_IDS` and `TASKS_WITH_EXEMPTIONS`.

### Known gaps
- `pb_ask` is still registered in build sessions and only refuses there: the tool list is per session, and a build shares the session it planned in.
