## Engineering standards

- Quality: the best current practice for this stack: clean, maintainable, secure; a proper fix, never a workaround. Names say what the thing is or does: no abbreviations beyond domain terms, no generic verbs like handleData or processInfo. Use modern idioms and the latest stable language and platform features, even where the surrounding code doesn't. When outdated code stands in the way, refactor it to current practice, planned as a task of its own.
- Dependencies: current, non-deprecated APIs and versions only. Upgrading dependencies is a change of its own, not part of a feature.
- Comments: concise, and only where they add what the code can't say (why, intent, constraints). They describe the code as it is, never its history: no dates, "decided", previous values or task ids; decisions stay in the spec.
- Tests: test behaviour, written to current best practice for this stack even where existing tests aren't; new test tooling is proposed as a task of its own. Never weaken an existing test. A test proves a fix only if it fails without it.
- Security: assume every entry point (API, UI action, command, message, file, webhook) will be abused by someone who controls its input, holds a stolen or another user's session, and replays or automates requests. Each operation checks who the caller is, what they may act on, and what they have proven; logic reused from another flow keeps that flow's preconditions (a write that is safe behind an emailed token is not safe behind a session alone). Security-relevant changes get tests for their abuse cases, written from the attacker's side. When something gains trust or changes hands (verified, accepted, promoted, transferred), whatever was set up before the proof by someone who hadn't proven anything (credentials, sessions, linked identities, settings) is discarded or re-proven, not inherited.
- One source of truth: a rule or canonical form that already exists (in the database: normalization, uniqueness, constraints; or in a shared helper) is used, never re-implemented. Compare against the database's own form in SQL; a second copy of a rule drifts, and the gap between copies is a bypass.
- Robustness: at a boundary, assume input is hostile or broken (sizes, ranges, encodings, duplicates, order, concurrent calls); business rules can't be bypassed by quantity, repetition, reordering or racing; every request's work is bounded; a failure halfway leaves consistent state. Values that will be stored, compared or sent (addresses, identifiers, URLs) are validated strictly: no control characters or whitespace, and nothing that Unicode normalization would change. Inside the boundary, rely on invariants (types, constraints, transactions), not repeated checks.
- Consistency and concurrency come from the database: one request is one transaction on one connection. Use constraints, single atomic statements (`ON CONFLICT`, `UPDATE … RETURNING`) or row locks; not check-then-write in application code, retries, or extra transactions (`REQUIRES_NEW`), unless the reason is stated where it's used. State transitions are guarded by the current state (`WHERE status = …`), so repeating one is a no-op and a fact recorded once (a verification or creation time) is never overwritten.
- Before calling a change done, re-read the diff as an attacker and as a race: a stolen session, a replayed or concurrent request, a look-alike or malformed input, an attacker who acted before the victim, a failure halfway. Search for existing copies of any rule you touched.

## Project map

### Layout
- `index.ts` is the composition root; `kit.ts` holds the shared machinery and the trust boundaries (the approval gate, `driftStop`, the spec guards). Every command and fresh role lives in its own file named after it; the pure logic sits apart in `phase.ts`, `next.ts` and `command-guard.ts`.
### Security invariants
- A repair lap cannot promote itself: it writes only through `pb_write_spec` (format gates, spec guards), its probe `pb_try` is read-only, and `pb_spec_fix_done` accepts a report only from the session named in `Progress.fix`, only for the finding numbers that lap was shown. (security)
- The claim check records a `spec-check` event and never a `spec-review`, so no repair run can satisfy the build's review gate. (security)
- `pb_explore` and `pb_try` run guarded: their processes start with `--no-extensions`, so pb's own shell hook is not there; `fresh-guard.ts` is loaded into both with `-e`, its settings handed over in `PI_PB_GUARD` (`guardSettings`, kit.ts), and it fails closed (no shell) without them. (security)
- Their shell rules live once in `command-guard.ts`, shared with hooks.ts: the explorer's shell is an **allowlist** of read-only inspection commands, a probe's refuses what `remoteWriteRefusal` matches, and both run with credentials removed (`scrubPrefix`; Pi's own process keeps its model keys). (security)
- The env scrub, not the pattern list, is what keeps a probe off production: never weaken it to make a probe work, and it has no configuration on purpose. (security)
- Shell limits come from `commandCap` everywhere: the project's own long commands (`longCommands`, kit.ts) get `longCommandSec`, ordinary ones `commandTimeoutSec`, and inside a run no command gets more than the run has left. A Pi bash timeout posts a note naming the limit that fired and how to raise it (hooks.ts, fresh-guard.ts).
- The explorer run itself is bounded by `explorer.idleSec` (no progress: no tool call and no finished message, `runFresh`'s `idleMs`) and `explorer.timeoutSec`; a probe by `probeTimeoutSec`.
- A spec may cite a sibling repository (`../<repo>/<path>:<line>`, a change spanning a backend and its frontend) only through `resolveSiblingFile` (`extensions/pb/map.ts`): the real path (links followed) must stay inside the folder that holds the project and outside the project, with no dot-named part, never on a filesystem root. (security)
- Anything else is "not in the project" and the error says nothing about the file it names; `specPathErrors` and `unresolvedAnchors` share `resolveSiblingFile`. (security)
- A spec name never becomes a path directly: `specDir` (`extensions/pb/store.ts`) is the only spec-name→path point; anything that is not `KEBAB_NAME` (`extensions/pb/names.ts`) or the name of an existing spec dir throws before a path is built. (security)
- A build tool may only record into the build its own session owns, and only the current step: `specForSession` (realpath-compares the session file) → `buildOfSession` throws unless `phase === "building"`, and `pb_task_done`/`pb_tests_red` refuse `params.task !== p.current` (`extensions/pb/build-loop.ts`). The tool is never the place to relax this. (security)
- Review sessions are read-only by the `tool_call` guard (`extensions/pb/hooks.ts`), which blocks every tool outside `REVIEW_SESSION_TOOLS` for any session holding a `reviewSession` record — not just `edit`/`write`, because a tool Pi activates after `session_start` (a late-connecting MCP server's, say) must not reach a reviewer. (security)
- The review pass re-marks the new session fail-closed inside its `withSession` (`extensions/pb/review-flow.ts`), so stolen or expired handover state cannot yield a writable reviewer; `pb_report_findings` separately refuses any session without that record. (security)
- A repair lap can write only its own spec: the same `tool_call` guard blocks every tool outside `REPAIR_SESSION_TOOLS` (`extensions/pb/kit.ts`: read/grep/find/ls, `pb_try`, `pb_ask`, the spec tools and `pb_spec_fix_done`) for a session owning an open lap, and `pb_write_spec`/`pb_update_spec` separately refuse a name other than that lap's spec. (security)
- Planning changes nothing outside the machine either: in a planning session the `tool_call` guard refuses a shell command `remoteWriteRefusal` (command-guard.ts) matches — the probe's rule, reads still allowed — and refuses `edit`/`write` inside any sibling git repository (`siblingRepoOf`, repos.ts), named by a spec or not. (security)
- A spec's sibling repositories (`Also changes: ../<repo>`, parsed into `ParsedSpec.repos`, checked by `specRepoErrors` at a ready write) are covered wherever the project is: the build records `Progress.repoBases`, every checkpoint row snapshots each (`repoSnapshots`, `Checkpoint.repos`) and `/pb:undo` restores them under the same drift guard, its own row carrying them for a redo.
- A sibling's change since its base is part of the review's frozen diff and changed-file list, under its name, and `/pb:commit` offers their files as `../<repo>/<path>` and commits per repository with one message. A follow-up review's "nothing changed" shortcut checks each sibling from its snapshot at the last review (`ReviewState.repos`; none recorded = never skipped).
- pb's own checks are project-only on purpose: the build's final step, a fix lap's and the review's run the project's commands, and a sibling's behaviour is proven by the spec's `Test:` lines; likewise the planning change report, since planning already blocks edits in siblings.
- Planning mode's project protection is three-layer: the `tool_call` hook blocks `edit`/`write` at in-project paths for sessions in `planningSessions()`; `agent_settled` (build-start.ts) posts files differing from the planning snapshot at each turn end (`changedPaths`); `reviewPlanningChanges` asks keep-or-restore. Paths outside the project are allowed (scratch). (security)
- A review cannot mutate what it judges: the code-review session's tool set is `REVIEW_SESSION_TOOLS` (read/grep/find/ls plus `pb_report_findings`, no shell), and the fresh spec reviewer, verifier and adversarial pass get the same four read tools (the pass reports through `REVIEW_TOOLS`). (security)
- The change reaches them as `reviewDiff` — one `gitDiff` + `untrackedText` capture taken right after the review's `before` snapshot, capped at `REVIEW_DIFF_CHARS` — so a check or a later edit cannot change it; the verifier is handed that same diff. (security)
- Model-authored text never reaches a markdown container unsanitised: `safeLine`/`safeBlock` (`extensions/pb/markdown.ts`) strip control characters before comment markers and repeat to a fixpoint; every stored ledger field goes through `ledgerField`/`cap`. Pinned by the test "review ledger: an injected marker cannot reach the project map". (security)
- `Test:` commands run through `runVerify` with `shell: true` on purpose (they are spec-approved shell); `suspiciousCommand` (`extensions/pb/kit.ts`) flags shell chaining/network in `specWarnings` and the pre-approval dry-run declines to execute those commands — never move that check out of the flag. (security)
- A passing spec review covers exactly the text it saw: `ensureSpecReviewed` (`extensions/pb/spec-review.ts`) reuses a `spec-review` event only while `specHash(markdown)` matches, and only a P0 blocks. (security)
- Two doors reach that one pass — on the way into a build, and on demand from `/pb:spec-review` (`reviewDoor(name, "build" | "standalone")` carries only the wording; the recorded event and the reuse are shared), so a standalone pass is what the following build rides on instead of reviewing again; `--fresh` is the deliberate exception that pays for another pass at the same text.
- Neither door re-reviews a spec edited after T1 started: that is the code reviewer's. The event also stamps the `head` the pass read the repo at, and a re-posted verdict says so when HEAD has moved — information only, never a second gate (uncommitted drift moves no HEAD).
- `/pb:spec-review` records a plan-level verdict but gates nothing: only `startBuild`'s own re-read of the text (`specHash` against the reviewed bytes) precedes `approveSpec`, so a mid-build standalone pass cannot carry a build past an unreviewed or edited contract. (security)
- pb's own check outranks a review's reviewers: `/pb:review` runs `finalCheckCommands` (kit.ts, the same list the build's final step and a fix lap run) then each finished task's `Test:` (skipping a `suspiciousCommand`), and stores the failures on the run (`ReviewRun.failedChecks`); `reviewMessage` turns a PASS over any into UNVERIFIED. Never let a review pass over a red check.
- `/pb:build` asks at most one question about the build itself, after the spec review: the build-start screen (`startBuild`, build-start.ts) lists every concern `preBuildChecks` and `openP1s` collect (an unbuilt dependency, a red baseline, the review's P1s) plus where to build when the session is full or the model switches, and offers build (here/fresh), repair first (P1s only) or stop.
- Keep-or-restore of files changed while planning stays its own question; a new concern is added to that build-start list, never as a dialog of its own.
- One build per working tree (`otherBuilds`, build-start.ts): a build's base is HEAD, so its snapshots, review diff, checks and commit see the whole tree; another spec building now (its session file written within `longCommandSec` plus 10 minutes) refuses the start, and another spec's uncommitted files since its base are a concern there. A deleted session file never reads as live.
- A timed-out choice posts what pb did (`choose`, kit.ts), and while any dialog is open the footer reads "pb · waiting for your answer" (`ui_prompt_start`/`ui_prompt_end`, hooks.ts).
- pb writes to git history only through `/pb:commit` (commit.ts), and only after the human confirms in its editor: the editor holds the message (built from the spec by `commitMessageFor`, no model) and the offered files, and `readCommitEditor` keeps only paths pb offered, so an edited line can never add one. (security)
- `/pb:commit` stages and commits explicit paths (`git add -- <paths>`, `git commit --only -- <paths>`), never `-A`, never `.pi/` (so never the spec), and leaves anything else staged as it was. Each commit is a `commit` event (sha, files, subject): the next message describes what changed since it, and `whereNext` moves a reviewed spec from commit to archive. (security)
- `/pb:archive` asks before archiving a spec that still owes work (`owedOnArchive`, archive.ts: build unfinished, never reviewed, last verdict not pass, open P0–P2 findings) and refuses a name that isn't `KEBAB_NAME` before any path is built; headless, it archives and says what was left.
- A `/pb:fix` lap's outcome is pb's, not the lap's: `driveFix` (`extensions/pb/fix.ts`) runs `checkAfterLap` after every report — each reproducing test the lap saw fail must pass now, then `finalCheckCommands` — and a red result keeps the lap's findings open and hands the failure to the next lap.
- `pb_fix_done` counts a finding as fixed only with a `pb_fix_red` proof (the command pb ran and saw fail, stored by number in the `FixSession` record) or an `untested` reason, and reports are read by finding number (`fixedIds`), never by title. A lap is a `kind: "fix"` checkpoint row (no conversation point) and its `check` events stay out of per-task stats.
- A `/pb:fix` lap may change only its own spec's Design and Decisions: `pb_update_spec` refuses any other section, another spec and a status change for a session holding a `fixSession` record, and `pb_write_spec` refuses it outright (`extensions/pb/spec-tools.ts`). Both sections are outside `contractText`, so a lap's edit never needs re-approval, and it keeps the spec's `writtenIn`. (security)
- A contract change stays a skipped finding for a spec revision, never a fix lap's edit.
- Handover state is single-use and scoped: `takeCarry` (`extensions/pb/store.ts`) consumes the handover file in the pb state dir, enforces a 60-minute TTL, and returns it only to the child of the recorded parent session; every cancel/throw path calls `clearCarry` (store.ts, build-start.ts, repair.ts, review-flow.ts). (security)
- A leaked carry turns the next new session from the home session into a read-only review session, which is why no failure path may leave one. (security)
- `/pb:undo` restores files, task state and conversation but never moves the branch. Files that differ but no finished step's row recorded (`Checkpoint.files` from the target on) are named, and the human may keep them (`restore`'s `paths`); headless, everything goes back.
- The task snapshot in each checkpoint row is what drops red proofs with the files. A repair lap's row also carries the spec text and phase, restored from the row because the spec is outside the snapshots, behind the same drift guard; its result counts what `restore` actually restored plus the spec it rewrote, never the pre-dialog diff count.
- `/pb:undo` numbers its row from the highest `u` id in the rows it keeps, never from a count over the pre-undo list: the undo drops the rows from the target on, and a count over those can re-issue an id a surviving row still holds — `/pb:undo uN` resolves to the first match, so a duplicate would restore an older state than the tip printed.
### Docs that are runtime input (extensions/pb/guide.md, extensions/pb/help.ts, README.md)
- `guide.md` is parsed at runtime: ` pb:tip key ` regions are the only source of "What now" text (`tip()`, defined in help.ts, used across the phase modules), and `pb:topic` regions are `/pb:help` sections. Using `tip("x")` without the region fails the test "help: every What-now block the code uses exists in the guide".
- `BINDING_SECTIONS` (`spec.ts`) is the single list every build prompt names for the model to read (`specReference`), and the guide and README must state it in the exported order (test "binding: the guide and README list the binding sections in the exported order"). Nothing renders or shortens the sections any more: the spec file is one read away.
### Tests + build
- `npm test` → `node --test "test/*.test.mts"` (504 tests, ~80 s: the files run in parallel); `npm run typecheck` (strict, with `noUnusedLocals`/`noUnusedParameters`, tests included); `npm run check` runs both (CI matrix: Node 22/24/26). npm + `package-lock.json`.
- The end-to-end suite is split by area over one harness, `test/harness.mts` (the simulated Pi, `setup()`, the `SPEC()` fixtures and scripted agents), into `test/plan.test.mts` and its spec, build, review and core siblings there. A new test goes in its area's file and imports only what it uses (the typecheck refuses an unused import); a helper shared by two files belongs in the harness.
- `phase.test.mts`, `guard.test.mts` (the shell rules and `fresh-guard.ts`) and `prompts.golden.test.mts` are unit-level.
- `node scripts/verify-test.mjs [--file <file>] "<exact test name>" ...` is the per-task proof: it exits 0 only when every name has a TAP `ok N - <name>` line and the report says `# fail 0` (a `# SKIP` is not a proof), because a zero-match `--test-name-pattern` run itself exits 0. Names are regex-escaped; without `--file` it runs the whole suite; dev-only (outside `package.json` `files`).
- `test/verify-fixture.test.mjs` is deliberately **not** run by `npm test`: its name sits outside the `test/*.test.mts` glob the suite runs. The prover's own tests drive it through `--file`, so they never nest the real suite.
- Peer ranges must stay identical in `package.json` and `package-lock.json` or `npm ci` refuses in CI: after touching a peer, run `npm install --package-lock-only`. Pinned by "deps: the lockfile peer ranges match package.json".
- Pi's host-provided packages (`typebox`, `@earendil-works/pi-*`) are never in `dependencies` — Pi refuses such a package at startup and can end up with two copies of TypeBox. They are peers (`typebox` as `"*"`) and kept in `devDependencies` so typecheck and tests resolve them outside Pi. Pinned by "deps: Pi's host-provided packages are peers, never dependencies".
- The suite drives the real commands and tools against a simulated Pi; `PI_PB_PI_COMMAND` points fresh sub-processes at `test/mock-pi.mjs`. Its report modes and env knobs are named in that file's header: `MOCK_SPEC_REVIEW` for the spec reviewer (its `badfile` mode reports a finding whose file doesn't exist), `MOCK_SETTLE` for the claim check, `MOCK_VERIFY` for the verifier.
- `MOCK_SPEC_BRIEF_OUT` captures the reviewer's brief, `MOCK_SPEC_EDIT` simulates a human editing the spec mid-review, and `MOCK_ABUSE_ARGS_OUT` / `MOCK_SPEC_ARGS_OUT` capture a fresh run's argv (its `--tools` allowlist); the mock refuses a report through a tool `--tools` does not name.
- `setup()` sets `reviewer.idleSec: 0.2` (a review pass ends as soon as its session goes idle) and an empty `specReviewer` (the review always runs); `PI_CODING_AGENT_DIR` is redirected to a temp dir so nothing touches the real user agent dir. `MOCK_VERIFIER_BRIEF_OUT` captures the verifier's brief.
- `written()` asserts an error-free `pb_write_spec`, so any new write gate must be satisfied by the shared fixtures: `SPEC()`, whose Tasks default to `TASKS_PLAIN`, with `TASKS_WITH_A_REFACTOR` (its `(refactor)` title is the red-gate exemption) and `THREE_TASKS` (the coherence pass) beside it.
### Known gaps
- `pb_ask` is still registered in build and lap sessions and only refuses there (a build, a fix lap, a hardening lap: `ask.ts`): the tool list is per session, and a build shares the session it planned in. A manual `/pb:spec-fix` lap may ask, always with `askTimeoutSec`.
- Answers given while planning are kept in the planning record (`recordPlanningAnswer`) and handed to the spec prompts, never only to the conversation.
- The row dedupe is proven at `appendCheckpoint` (unit) and every build test drives `beginTask`, but `beginTask`'s dedupe-false branch is not reachable through the real flow: moving the task-status/current/attempt updates inside its `if (appendCheckpoint(...))` (`extensions/pb/build-loop.ts:116`) would stay green.
